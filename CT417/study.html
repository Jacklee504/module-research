Lecture and exam route

Work through the current lectures and all four recurring 20-mark paper families. Write each answer before opening its plan; the paper-linked topics without a current slide still need full preparation.

  • Git and team workflow

    2025/26 Q1(d) [5]: causes, prevention and resolution of merge conflicts; 2024/25 Q1(b) asks for Git commands. Explain a conflict and a safe resolution sequence.

    Reveal answer plan
    • Concurrent edits to the same lines or related code create conflicts when histories are integrated.
    • Fetch current main, merge or rebase into the feature branch, resolve each conflict deliberately, then test and complete the integration.
    • Keep branches small, sync often and open pull requests early. Review the final diff before merging.

  • Build and CI/CD

    2025/26 Q1(b)–(c), 5 marks each: design pull-request tests, image build and staging, then critique an unsafe deployment.

    Reveal answer plan
    • On a pull request: check out code, install dependencies, build, run tests and report failures before merge.
    • After merge: build and tag the image, push it to a registry, deploy to staging and run smoke tests before promotion.
    • Keep production deployment behind a gate and retain a known working image for recovery.
    Canvas build toolsCanvas GitHub Actions2025/26 paper
  • Docker deployment

    2025/26 Q1(a) [5]: diagnose a manifest unknown error, correct the missing image tag and redeploy using Git and Docker commands.

    Reveal answer plan
    • Check the workflow commit, image name and tag; inspect local images and available registry tags.
    • Build or retag the intended image, push that exact tag, then confirm the staging server pulls it successfully.
    • Prefer a versioned tag tied to a commit so the deployed build and rollback target are clear.
    Canvas deploymentCanvas Docker overview2025/26 paper
  • Requirements and change

    Current lecture support for testable requirements and controlled change. Treat as supporting coverage. Turn an ambiguous request into a testable requirement.

    Reveal answer plan
    • Identify the stakeholder, need, constraints and acceptance condition before writing a specific requirement.
    • Check completeness, consistency and feasibility with the stakeholder.
    • Record the proposed change, impact on scope and tests, decision and trace to the implemented work.

  • Testing and security tools

    2025/26 Q2(a)–(d), 5 marks each: compare SAST and DAST, diagnose ZAP reports, improve SonarQube feedback and target low-coverage payment code.

    Reveal answer plan
    • Compare timing, source access, defect types and a tool example for SAST and DAST.
    • For ZAP, give two specific failure causes and a resolution for each, such as the app not running or incorrect target/authentication settings.
    • For SonarQube and coverage, justify faster feedback without excluding production code; inspect branch or line coverage and add focused tests to critical paths.

  • Vulnerabilities and reliability

    2025/26 Q3 [20]: short definitions [1+1+2], incident MTBF and improvements [4+2+4], then buffer overflow and two countermeasures [6].

    Reveal answer plan
    • Define vulnerability, countermeasure and zero-day precisely before moving to the scenario.
    • For each incident use the paper's stated MTBF = MTTD + MTTR assumption; average the three totals, identify the best incident and separate detection from recovery improvements.
    • Explain the out-of-bounds write and how an attacker may alter adjacent memory, then justify two distinct safeguards.

  • Refactoring and design patterns

    2025/26 Q4 [20]: justify refactoring [4], match two design problems to patterns [3+3], then replace role conditionals with an abstraction, subclasses and a factory [2+4+4].

    Reveal answer plan
    • Explain how extracting shared behaviour reduces duplication and makes extensions safer.
    • Match a concrete problem to each pattern and explain the improvement, for example Strategy for payment choices and Adapter for a notification API.
    • Show the User abstraction, role-specific implementations and a UserFactory; keep controller code dependent on the abstraction.
