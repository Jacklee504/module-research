Priority 1 - CI/CD, GitHub Actions, Docker Deployment, And Git Workflows

Frequency: 3/3 Effirul papers. This is the strongest current CT417 question family.

Appears as:

  • 2023/24 - Q4(a)-(b) - list CI advantages and discuss CI/CD adoption pitfalls.
  • 2024/25 - Q1(a) - propose four CI/CD pipeline improvements for FoodieGo.
  • 2024/25 - Q1(b) - write Git commands for status, add, commit, push, and merge feature branch into main.
  • 2024/25 - Q1(c) - explain a GitHub Actions YAML build job for a Java/Maven app, tests, coverage, Docker build, and registry push.
  • 2025/26 - Q1(a) - diagnose and fix a failed Docker pull: manifest unknown for ghcr.io/skybankai/app:latest.
  • 2025/26 - Q1(b) - design a simplified GitHub Actions pipeline for a Node.js microservice.
  • 2025/26 - Q1(c) - identify risks in a bad pipeline where tests only run on main, every commit deploys to production, and no rollback exists.
  • 2025/26 - Q1(d) - explain how merge conflicts arise and how to prevent and resolve them.

Consolidated most-asked question:

Given a company with manual testing, integration conflicts, insecure releases, failed deployments, and weak rollback, propose a practical GitHub Actions CI/CD workflow and show how to diagnose, fix, and safely deploy changes using Git and Docker.

Reusable answer: Start with pull-request checks: checkout, install dependencies, run tests, run coverage, and run security scans before merge. On merge to main, build a versioned Docker image, push it to the registry, deploy to staging, run smoke tests, and only then promote or deploy onward. Use feature branches and PR reviews to control integration. Avoid direct production deployment from every commit without gates or rollback. For Docker manifest errors, check that the expected image name and tag exist, identify whether the image was pushed under a commit SHA or different tag, then retag or rebuild and push the expected tag before redeploying.

Command patterns worth knowing:

git status
git add .
git commit -m "Implemented new feature."
git push origin feature-branch
git checkout main
git pull origin main
git merge feature-branch

docker pull ghcr.io/skybankai/app:latest
docker build -t ghcr.io/skybankai/app:latest .
docker push ghcr.io/skybankai/app:latest

Merge-conflict answer structure:

  • Explain cause: two branches modify the same lines, nearby code, or related files and Git cannot automatically combine them.
  • Prevent: small branches, frequent pull/rebase from main, early PRs, team communication around shared files, and avoid mixing refactors with feature work.
  • Resolve: fetch latest main, rebase or merge, inspect conflict markers, combine or choose the correct code, run tests, git add, continue the rebase or complete the merge, then push the branch.

Priority 2 - SAST, DAST, SonarQube, OWASP ZAP, And Coverage

Frequency: 2/3 papers as a full 20-mark question, with JUnit also appearing in 2023/24.

Appears as:

  • 2023/24 - Q4(c) - design JUnit test cases for a simple Java Calculator.add() method.
  • 2024/25 - Q2(a)-(c) - compare SAST and DAST, explain why they belong in CI/CD, and state the role of code coverage.
  • 2024/25 - Q2(d) - propose two SonarQube optimisations, with justification and trade-offs.
  • 2024/25 - Q2(e) - diagnose OWASP ZAP pipeline failures and missing reports.
  • 2024/25 - Q2(f) - use coverage tools to find low-coverage Java business logic and increase coverage without slowing CI.
  • 2025/26 - Q2(a) - compare SAST and DAST by lifecycle timing, vulnerability type, source-code access, and tool examples.
  • 2025/26 - Q2(b) - identify two likely OWASP ZAP technical failure causes and practical resolutions.
  • 2025/26 - Q2(c) - optimise SonarQube without reducing scan quality.
  • 2025/26 - Q2(d) - use JaCoCo, Istanbul, or Coverage.py to identify low-coverage payment code and improve coverage efficiently.

Consolidated most-asked question:

Explain how SAST, DAST, unit testing, code coverage, SonarQube, and OWASP ZAP fit into a CI/CD pipeline, then troubleshoot performance or reporting problems without reducing useful scan quality.

Reusable answer: SAST analyses source code or compiled code before the application runs, so it is useful early in CI for code-level flaws and insecure patterns. DAST tests a running application from the outside, so it is useful against staging or production-like environments for runtime and configuration issues. SonarQube can be optimised with careful exclusions for generated files, dependencies, build outputs, and irrelevant artefacts, plus pull-request analysis focused on new code while full scans still run on main. OWASP ZAP failures often come from scanning before the app is running, wrong target URLs, authentication/session problems, blocked network access, or reports not being exported as CI artefacts. Coverage tools highlight untested files, methods, and branches; increase coverage by targeting critical paths and adding focused unit tests rather than slowing every pipeline with broad end-to-end tests.

Keep these distinctions separate:

  • SAST: early, static, source-aware, examples include SonarQube, Checkmarx, Semgrep, or CodeQL.
  • DAST: later, dynamic, no source-code requirement, examples include OWASP ZAP or Burp Suite DAST.
  • Coverage: tells you which code was exercised by tests; it does not prove correctness by itself.
  • SonarQube optimisation: exclusions and PR/new-code analysis are valid, but do not exclude real production code.

Priority 3 - Vulnerability, Countermeasures, Zero-Day Lifecycle, Metrics, And Buffer Overflow

Frequency: 3/3 Effirul papers. This is the most repeated definition/security family.

Appears as:

  • 2023/24 - Q3(a)-(e) - define vulnerability, countermeasures, zero-day vulnerability, zero-day lifecycle, and buffer overflow exploitation.
  • 2024/25 - Q3(a)-(f) - repeat vulnerability, countermeasures, zero-day, five-stage lifecycle, buffer overflow exploitation, and two buffer-overflow countermeasures.
  • 2025/26 - Q3(a)-(c) - repeat vulnerability, countermeasures, and zero-day vulnerability.
  • 2025/26 - Q3(d) - calculate average MTBF from MTTD and MTTR, identify best incident, and recommend MTTD/MTTR improvements.
  • 2025/26 - Q3(e) - define and explain buffer overflow exploitation and discuss two countermeasures.

Consolidated most-asked question:

Define key security terms, explain the zero-day lifecycle, calculate operational incident metrics, and explain how buffer overflow attacks work plus how to reduce them.

Reusable answer: A vulnerability is a weakness that can be exploited to violate security. A countermeasure is a safeguard that reduces the risk, likelihood, or impact of exploitation. A zero-day vulnerability is unknown to, or unpatched by, the vendor at the time attackers can exploit it. Its lifecycle can be explained as discovery, weaponisation/exploit development, active exploitation, disclosure/detection, and patching/remediation. A buffer overflow occurs when a program writes more data into a fixed-size buffer than it can hold, overwriting adjacent memory such as local variables or a return address. Countermeasures include bounds checking, safer library functions, stack canaries, ASLR, DEP/NX, compiler hardening, input validation, and using memory-safe languages.

2025/26 metrics pattern:

  • Use the question's given assumption even if it simplifies the real definition: MTBF = MTTD + MTTR for each incident.
  • Incident values: 4 + 2 = 6, 0.5 + 1 = 1.5, 6 + 4 = 10.
  • Average: (6 + 1.5 + 10) / 3 = 5.83 hours.
  • Best operational performance is Incident 2 because it has the lowest MTTD, lowest MTTR, and lowest downtime.
  • MTTD improvements: automated alerting, centralised logs, alert correlation, security monitoring, SAST/DAST gates.
  • MTTR improvements: rollback, feature flags, blue-green/canary deployment, incident runbooks, automated redeploy or patch pipelines.

Priority 4 - Refactoring, Design Patterns, Polymorphism, Factory Pattern, And Open/Closed Principle

Frequency: 2/3 papers as the full final question. It is extremely strong in the newest two papers.

Appears as:

  • 2024/25 - Q4(a) - explain the importance of design patterns.
  • 2024/25 - Q4(b) - explain why refactoring improves code reusability.
  • 2024/25 - Q4(c) - refactor separate customer/manager authentication methods using an abstract User class and polymorphism.
  • 2024/25 - Q4(d) - refactor account creation using a UserFactory.
  • 2024/25 - Q4(e) - refactor the factory so adding roles such as Admin does not modify createUser, following the Open/Closed Principle.
  • 2025/26 - Q4(a) - explain why refactoring improves code reusability.
  • 2025/26 - Q4(b) - identify two concrete design problems and match each to an appropriate design pattern.
  • 2025/26 - Q4(c) - refactor role-based conditionals using an abstract User interface/class, role-specific subclasses, and a UserFactory.

Consolidated most-asked question:

Given duplicated role-based controller code with conditionals for authentication or account creation, refactor it using object-oriented principles, a User abstraction, subclasses, and a factory that supports extension.

Reusable answer: Refactoring improves reusability by removing duplication, separating responsibilities, and making behaviour easier to extend without changing unrelated code. Replace role conditionals with polymorphism: define a User interface or abstract class with methods such as authenticate() or createAccount(), then implement role-specific subclasses such as Customer and Manager. A UserFactory centralises object creation so controllers depend on the abstraction rather than concrete role classes. To follow Open/Closed Principle more strongly, replace a hardcoded switch with a registry/map of role names to creator functions, so new roles can be registered without modifying the factory method itself.

Reusable pseudocode shape:

interface User {
  void authenticate(String username, String password);
}

class Customer implements User {
  public void authenticate(String username, String password) {
    // customer-specific authentication
  }
}

class UserController {
  public void authenticate(User user, String username, String password) {
    user.authenticate(username, password);
  }
}

Pattern-matching hints:

  • Many if/else or switch branches for user roles: polymorphism plus Factory Pattern.
  • Many payment methods selected by conditionals: Strategy Pattern or Factory plus Strategy.
  • Hardcoded email/SMS/push notification logic: Adapter, Strategy, or Observer depending on the wording.
  • Need to add new roles without editing old code: Open/Closed Principle and registration-based factory.

Agile Manifesto, Scrum, Changing Requirements, And Stakeholder Collaboration

Appears: 2023/24 - Q1(a)-(c) only.

  • Q1(a) - describe the Agile Manifesto and list two core principles.
  • Q1(b) - choose a relevant Agile principle and propose two solutions for changing requirements and evolving data sources.
  • Q1(c) - using business-stakeholder and developer collaboration, suggest five steps to improve model accuracy and reliability.

Explain Agile principles in a project scenario, then apply one principle to concrete delivery problems such as changing requirements, evolving data, and stakeholder concerns.

Reusable answer: Agile values individuals and interactions, working software, customer collaboration, and responding to change. For changing requirements, use short sprints, backlog refinement, sprint reviews, prioritisation, and regular stakeholder feedback. For reliability concerns, bring data scientists, developers, and business stakeholders together to define acceptance criteria, validate model performance, review real user feedback, adjust data sources, and iterate on the model with measurable quality targets.

Formal Specification And Z-Style Cursor Schemas

Appears: 2023/24 - Q2(a)-(e) only.

  • Q2(a) - list three advantages of formal specifications.
  • Q2(b) - describe an initial state schema for a cursor on a terminal display.
  • Q2(c) - define DownKeyNormal for pressing down when the cursor is not on the bottom line.
  • Q2(d) - define DownKeyAtBottom for pressing down when the cursor is on the bottom line.
  • Q2(e) - define the full behaviour.

List formal-specification benefits, then write small state and operation schemas for cursor movement with normal and boundary cases.

Reusable answer: Formal specifications reduce ambiguity, support precise validation of requirements, and can reveal inconsistencies before implementation. For the cursor schema, define state variables such as line and column with invariants like 1 <= line <= numLines and 1 <= column <= numColumns. The initial state sets the cursor to a valid starting position. DownKeyNormal increments line when it is below numLines and leaves column unchanged. DownKeyAtBottom handles the boundary case by keeping the cursor on the bottom line or otherwise defining the specified no-op behaviour. The full operation combines normal and boundary schemas.
