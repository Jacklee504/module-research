CT417 Revision

Automated Testing and Security Tooling

Explain what each automated check can reveal, when to run it, and what it cannot prove.

Rapid exam refresher

  • Unit/integration/coverage differ.
  • SAST source pre-run vs DAST live target.
  • reports/gates need reproducible authorised environment.

Purpose, scope and examiner demand

Automation gives developers fast feedback before a defect or security weakness reaches users. CT417 scenarios commonly connect unit tests, coverage, SAST, DAST, SonarQube and OWASP ZAP to a CI/CD pipeline.

Exam focus by part

  • Unit/integration/coverage differ.
  • SAST source pre-run vs DAST live target.
  • reports/gates need reproducible authorised environment.

Question-demand diagnosis and answer plan

Questions usually ask to compare tools, diagnose weak coverage or improve a failing quality gate. Define the tool; say its input and timing; state what it finds; give a concrete pipeline placement; add one limitation and response to findings.

Question-type cues

  • Application cue: ZAP fails without report.
  • Analysis cue: Payment code coverage low.

Definitions, notation and discriminating comparisons

  • Unit/integration/system test: isolated code, component interaction, whole-system behaviour.
  • Coverage: exercised code, often line or branch coverage; it measures execution, not correctness.
  • SAST: static application security testing, analysing source/bytecode without running the app.
  • DAST: dynamic testing of a running target through requests and responses.
  • SonarQube / OWASP ZAP: code-quality and static-analysis platform / web DAST scanner.
  • False positive/negative: incorrect warning / missed real issue.

Step-by-step methods and solution routes

  1. Classify the risk: logic regression, poor maintainability, dependency issue, or running-web-app weakness.
  2. Start with fast deterministic unit tests and lint/static quality checks on every PR.
  3. Run integration tests against representative services; publish test and coverage reports.
  4. Run SAST early because code is available; fix or triage findings according to severity.
  5. Deploy an isolated staging target and run DAST such as ZAP. Do not scan production without authorisation.
  6. Gate release on agreed severity/quality thresholds, then track exceptions rather than silently ignoring them.

Reasoning checkpoints

  1. Use and justify: Unit/integration/coverage differ.
  2. Use and justify: SAST source pre-run vs DAST live target.
  3. Use and justify: reports/gates need reproducible authorised environment.

Worked examples and method extensions

Practice

A payment API has 90% line coverage but an unauthenticated endpoint and duplicated validation logic. Recommend automated checks.

Model answer

Coverage alone is insufficient: it may execute code without asserting an outcome, and it may omit security paths. Add unit tests for authentication and invalid input, plus integration tests that call the endpoint with no token and expect rejection. SonarQube/SAST can flag duplicated code and insecure patterns during the PR. Deploy the API to a permitted staging environment and run ZAP/DAST to probe the running HTTP interface. Block release for confirmed high-severity findings, fix the endpoint, and retain the reports as pipeline evidence.

Medium practice — question demand

ZAP fails without report.

Plan / choice of method

Select the governing concepts before calculating: Unit/integration/coverage differ.; SAST source pre-run vs DAST live target.; reports/gates need reproducible authorised environment. Apply them only under the assumptions stated in the question, and compare the result with the required condition.

Worked answer

Target unreachable/not healthy/auth absent: wait health/correct URL/scoped creds. Persist JSON/HTML and distinguish scan error from findings.

Mark-winning points

Credit requires the named mechanism, all intermediate values or protocol states, the final conclusion, and these topic checks: Unit/integration/coverage differ.; SAST source pre-run vs DAST live target.; reports/gates need reproducible authorised environment.

Common trap

Running slow end-to-end scans first and delaying all PR feedback.

Graded practice and hard extensions

1. Foundation

Compare SAST and DAST in one table-like paragraph.

Answer check: SAST inspects code before running and finds source-level patterns early; DAST attacks/interacts with a running system and sees runtime configuration/interface behaviour. Neither replaces the other.

2. Exam bridge

A team says “coverage is 100%, so security testing is unnecessary.” Evaluate this claim and design a pipeline response.

Answer check: reject the claim, explain coverage’s limit, include assertions and negative tests, SAST, dependency checks, staging DAST, triage and a release threshold.

Hard practice — question demand

Payment code coverage low.

Plan / choice of method

Model the failure or boundary first, then apply these page-specific concepts in order: Unit/integration/coverage differ.; SAST source pre-run vs DAST live target.; reports/gates need reproducible authorised environment. Finish by checking the final state against the deadline, security property, consistency contract, or performance requirement.

Worked answer

Use report to target uncovered branches; add fast boundary/table tests and mocks in PR suite, retain integration/DAST in stage.

Mark-winning points

Credit requires the complete method sequence, explicit verification of the conclusion, and the limiting assumption/trade-off—not merely the recommended technology.

Common trap

Running slow end-to-end scans first and delaying all PR feedback.

Topic-specific traps and diagnosis

  • Claiming coverage proves absence of bugs or vulnerabilities.
  • Calling ZAP a source-code scanner, or SonarQube a replacement for live testing.
  • Automatically fixing every warning without validating false positives/context.
  • Running slow end-to-end scans first and delaying all PR feedback.

Exam marking checklist

  • State test level and tool input.
  • Contrast SAST and DAST accurately.
  • Place checks in a plausible pipeline.
  • Describe thresholds, triage and limitation.

Paper-year pattern note

Testing/security automation, SAST/DAST, SonarQube, ZAP and coverage form a strong recent 2023/24–2025/26 cluster. Tool names may change, so learn the testing principle and evidence each tool provides.
