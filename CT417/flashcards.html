2. SAST, DAST, SonarQube, OWASP ZAP, And Coverage

FrontBackYears
Compare SAST and DAST by timing, access, vulnerability type, and tools.SAST: early, source/compiled code, finds implementation flaws; tools: SonarQube, CodeQL, Semgrep. DAST: later, running app, black-box, finds runtime/config/web issues; tools: OWASP ZAP, Burp Suite.2024/25, 2025/26
Explain why SAST and DAST belong in a CI/CD pipeline.They automate security feedback, catch issues earlier, reduce late manual checks, and block insecure builds before release.2024/25
Explain the role and limitation of code coverage in unit testing.Shows which lines/branches/functions were exercised by tests; highlights untested areas but does not prove correctness.2024/25
Use coverage tools to identify low-coverage areas and improve coverage efficiently.Use JaCoCo/Istanbul/Coverage.py reports, target critical low-coverage paths, add focused unit tests, avoid slowing CI with broad slow tests.2024/25, 2025/26
Propose two SonarQube optimisations without reducing scan quality.Exclude generated/dependency/build artefacts and use PR/new-code analysis; keep full scans on main and never exclude production code.2024/25, 2025/26
Diagnose OWASP ZAP CI failures or missing reports and propose fixes.Causes: app not running, wrong URL/port, auth/session missing, blocked network, timeout, no report export. Fix: start app first, configure URL/auth/context, tune thresholds/timeouts, upload reports.2024/25, 2025/26

3. Vulnerabilities, Zero-Days, Metrics, And Buffer Overflow

FrontBackYears
Define vulnerability, countermeasure, and zero-day vulnerability.Vulnerability: exploitable weakness. Countermeasure: safeguard that reduces likelihood, impact, or exploitability. Zero-day: unknown/unpatched vulnerability that attackers may exploit before a fix exists.2023/24, 2024/25, 2025/26
Describe the zero-day vulnerability lifecycle.Discovery, exploit development/weaponisation, active exploitation, disclosure/detection, patching/remediation.2023/24, 2024/25
Define MTTD, MTTR, and the SkyBankAI MTBF assumption.MTTD = time to detect. MTTR = time to respond/recover/repair. In the question, MTBF = MTTD + MTTR per incident.2025/26
Calculate average MTBF from the SkyBankAI incidents.4+2=6, 0.5+1=1.5, 6+4=10; average (6+1.5+10)/3 = 5.83 hours.2025/26
Recommend improvements to reduce MTTD and MTTR.MTTD: automated alerts, logs, monitoring, alert correlation. MTTR: rollback, feature flags, blue-green/canary deployment, runbooks, automated redeploys.2025/26
Define buffer overflow and explain exploitation.Writing beyond a fixed-size buffer overwrites adjacent memory; attackers may overwrite variables/control data/return addresses to crash or redirect execution.2023/24, 2024/25, 2025/26
Discuss buffer overflow countermeasures.Bounds checking, input validation, safer functions/APIs, memory-safe languages, stack canaries, ASLR, DEP/NX, compiler hardening.2024/25, 2025/26

4. Refactoring, Design Patterns, Factory Pattern, And Open/Closed Principle

FrontBackYears
Explain why design patterns and refactoring improve maintainability/reusability.Patterns give proven reusable solutions and shared vocabulary. Refactoring removes duplication, separates responsibilities, improves structure, and makes behaviour easier to extend.2024/25, 2025/26
Given role-based if/else controller code, identify the design problems.Duplicated logic, tight coupling to concrete roles, poor separation of concerns, and controller changes needed whenever a new role is added.2025/26
Refactor role-based authentication/account creation using polymorphism and a User abstraction.Define User interface/abstract class with methods like authenticate()/createAccount(). Implement role-specific subclasses such as Customer, Manager, Admin. Controller depends on User.2024/25, 2025/26
Explain how a UserFactory supports the refactor.It centralises creation of role-specific User objects so client/controller code depends on the abstraction, not concrete classes.2024/25, 2025/26
Apply the Open/Closed Principle to a role factory.Use a registry/map of role names to creator functions/classes so new roles can be added without editing the existing factory method.2024/25
Identify design patterns for payment methods and notifications.Payments: Strategy, possibly Factory + Strategy. Notifications: Adapter for external APIs, Strategy for delivery type, or Observer for event-driven notifications.2025/26
