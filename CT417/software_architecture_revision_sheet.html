Software Architecture

Choose and justify a high-level structure against quality attributes, not fashion.

Rapid exam refresher

  • Architecture components/connectors/quality trade-off.
  • layers separate.
  • plugins use core/manager/extensions.
  • interfaces provide/require services.

Purpose, scope and examiner demand

Architecture makes the system’s major components, boundaries and communication decisions explicit. The current CT417 scope names microservices, serverless and API-first styles; older papers also include cloud, Docker and virtualisation. It remains in scope even where recent recurrence is weaker.

Exam focus by part

  • Architecture components/connectors/quality trade-off.
  • layers separate.
  • plugins use core/manager/extensions.
  • interfaces provide/require services.

Question-demand diagnosis and answer plan

An architecture question normally asks you to select, compare or critique a structure for a scenario. First list quality attributes such as scalability, latency, deployability, security, cost and team ownership. Then describe components/data flow, justify the style against those attributes, and name risks plus mitigations.

Question-type cues

  • Application cue: Compare layered and plugin reports system.
  • Analysis cue: Split monolith payments/notifications.

Definitions, notation and discriminating comparisons

  • Architecture / component / connector: high-level structure / major responsibility / communication path.
  • Monolith: one deployable application, often simpler to develop initially.
  • Microservice: independently deployable service around a bounded responsibility, communicating over APIs/events.
  • Serverless: provider-managed event/function execution with elastic scaling.
  • API-first: contract is designed and governed before consumers implement against it.
  • Quality attribute: non-functional property such as availability, modifiability or performance.

Step-by-step methods and solution routes

  1. State user actions, data sensitivity and expected scale, avoiding unsupported assumptions.
  2. Identify bounded responsibilities and ownership, for example catalogue, payment and notification.
  3. Choose a suitable style: a modular monolith for early simplicity; microservices for independently changing/scaling domains; serverless for variable event-driven work.
  4. Draw or describe request flow, authentication boundary, data ownership and failure path.
  5. Assess trade-offs: microservices add network failure, observability and distributed-data complexity; serverless can add vendor dependence and cold starts.
  6. Propose concrete safeguards: API versioning, timeouts/retries, tracing, least privilege and automated deployment.

Worked examples and method extensions

Practice

A small campus event app has a three-person team, low initial traffic and weekly changes. It may later add a separate ticketing partner. Recommend an architecture.

Model answer

Begin with a modular monolith exposing a documented API. Keep events, accounts and ticketing adapters in separate modules with tests and clear data ownership. This minimises operational cost and speeds a small team’s weekly changes. Put the partner integration behind an interface/API adapter so it can be replaced or extracted later. A microservice split now would add deployment, monitoring and distributed transaction complexity without demonstrated scale. If ticketing later has independent release/scale needs, extract it with versioned APIs, tracing and retry/timeout handling.

Graded practice and hard extensions

1. Foundation

Give one benefit and one risk of microservices compared with a monolith.

Answer check: independent deployment/scaling is a benefit; network, observability and distributed-data complexity is a risk.

2. Exam bridge

Compare serverless and containerised services for a bursty file-processing workload containing personal data.

Answer check: discuss event scaling/cost and cold starts/vendor controls versus container control/operational effort; include authenticated storage, least privilege, encryption, monitoring and retention.

Hard practice — question demand

Split monolith payments/notifications.

Plan / choice of method

Model the failure or boundary first, then apply these page-specific concepts in order: Architecture components/connectors/quality trade-off.; layers separate.; plugins use core/manager/extensions. Finish by checking the final state against the deadline, security property, consistency contract, or performance requirement.

Worked answer

Define ownership/contracts/sync-async connectors, observability/failure semantics and data consistency events/outbox; do not split merely by tier.

Mark-winning points

Credit requires the complete method sequence, explicit verification of the conclusion, and the limiting assumption/trade-off—not merely the recommended technology.

Common trap

Choosing an approach before naming quality attributes.

Topic-specific traps and diagnosis

  • Calling microservices automatically more scalable without considering data and operations.
  • Listing styles without drawing a boundary or data flow.
  • Confusing Docker (packaging) with an architecture style.
  • Choosing an approach before naming quality attributes.

Exam marking checklist

  • State scenario assumptions and quality attributes.
  • Explain components, connectors and data/security boundary.
  • Justify the chosen style and an alternative.
  • Give risks and mitigations.

Paper-year pattern note

Architecture is explicitly supported by the current module scope, but the 2019/20 architecture/virtualisation emphasis is less visible in the two newest papers. Treat it as important scope coverage, not a high-confidence recurrence.
