CT417 Revision

Refactoring and Design Patterns

Improve design without changing observable behaviour, then explain why the new structure is easier to extend.

Rapid exam refresher

  • Refactor preserves behaviour with tests.
  • Factory creation, Strategy variation, Observer events.
  • polymorphism removes type switch.
  • Open/Closed extends safely.

Purpose, scope and examiner demand

Refactoring is a behaviour-preserving change to internal code structure. A design pattern is a reusable design idea, not a class library. CT417 recent papers use role conditionals, abstractions and Factory Pattern to test maintainable design reasoning.

Exam focus by part

  • Refactor preserves behaviour with tests.
  • Factory creation, Strategy variation, Observer events.
  • polymorphism removes type switch.
  • Open/Closed extends safely.

Question-demand diagnosis and answer plan

Questions give code or a design smell and ask for an improvement. Identify the smell, state the invariant behaviour, propose a small sequence of refactorings, explain class responsibilities and show how the pattern reduces future modification risk. Mention tests before and after.

Question-type cues

  • Application cue: Controller has role methods/switch.
  • Analysis cue: New notification channel edits everywhere.

Definitions, notation and discriminating comparisons

  • Code smell: warning sign such as duplicated code, long conditional or feature envy.
  • Extract method / replace conditional with polymorphism: isolate responsibility / move varying behaviour into subclasses or strategies.
  • Interface / abstract class: contract only / shared contract plus common state or implementation.
  • Factory: centralises object creation behind an interface.
  • Open-closed principle: open to extension, closed to modifying stable client code.

Step-by-step methods and solution routes

  1. Write or identify characterisation tests to capture current behaviour.
  2. Find variation: e.g. a role string drives repeated if/else logic.
  3. Extract a stable interface such as UserRole, and give each role its own implementation.
  4. Move role-specific actions into those implementations. Keep clients dependent on the abstraction.
  5. Use a Factory to map an approved input to the appropriate role object, validating unknown input.
  6. Run tests after each small step. Explain how adding a role now means adding a class/registration rather than editing every conditional.

Reasoning checkpoints

  1. Use and justify: Refactor preserves behaviour with tests.

Worked examples and method extensions

Practice

if (role == "admin") delete(); else if (role == "editor") edit(); else view(); appears in three controllers. Refactor it.

Model answer

First test that admin can delete, editor can edit but not delete, and viewer can only view. Define a Role interface with canEdit() and canDelete(). Implement AdminRole, EditorRole and ViewerRole. A RoleFactory converts validated stored role values into these objects. Controllers ask role.canDelete() rather than repeat a string conditional. Behaviour is preserved but permission logic has one owner; a new auditor role extends the model with less scattered change. The factory must reject unknown roles, and authorisation must still be enforced server-side.

Graded practice and hard extensions

1. Foundation

Why is changing variable names usually refactoring, while adding a feature is not necessarily refactoring?

Answer check: refactoring changes internal structure while preserving externally observable behaviour; a new feature changes behaviour and needs separate design/testing.

2. Exam bridge

Given a long conditional selecting notification types, propose Factory plus polymorphism and evaluate one benefit and one cost.

Answer check: identify interface, implementations, creation point and tests; benefit is localised extension, cost is extra classes/indirection for a small stable problem.

Topic-specific traps and diagnosis

  • Calling a rewrite “refactoring” when it changes requirements without tests.
  • Adding a pattern just because it has a name.
  • Using inheritance where composition/strategy would make variation clearer.
  • Forgetting factory validation or assuming UI role checks secure the backend.

Exam marking checklist

  • Name the smell and preserved behaviour.
  • Describe classes, responsibilities and creation.
  • Use tests as the safety net.
  • Give benefit, trade-off and extension example.
