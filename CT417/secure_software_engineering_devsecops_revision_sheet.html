CT417 Overview CI/CD and Git Testing and security tooling

CT417 Topic Guide

Secure Software Engineering and DevSecOps

Use security evidence throughout delivery: prevent early, test automatically, release safely, and respond when production evidence changes the risk.

What repeatedly appears in the papers

The recent papers test this as a 20-mark company scenario, not as a request to list DevSecOps buzzwords. 2024/25 and 2025/26 repeatedly ask you to diagnose a pipeline or security-tooling failure, propose practical changes, and justify the trade-offs.

  • Secure CI/CD design: automate integration, tests, security checks, staging, controlled release and rollback.
  • SAST versus DAST: compare when they run, what they see, what they detect, source-code access, and a tool example.
  • Tool failure and speed: diagnose OWASP ZAP reporting failures; improve SonarQube feedback without silently lowering assurance.
  • Coverage and third-party risk: use coverage evidence to target tests; identify, assess and remediate vulnerable dependencies.

Rapid refresher: the control map

Delivery pointWhat to name in an answerWhy it earns credit
Pull requestSmall branches, review, unit/integration tests, SAST, secret and dependency checksFinds defects before merge and reduces integration conflict.
StagingProduction-like environment, automated regression tests, OWASP ZAP against an authorised target, published reportsTests the running service and exposes configuration/integration faults before production.
ReleaseVersioned Docker image, security/quality gate, controlled deployment and rollbackLinks the tested build to a recoverable release, rather than deploying an untraceable latest build.

How to answer the scenario questions

  1. Underline each stated failure: for example, manual testing, merge conflicts, late dependency CVEs, or no reports from ZAP.
  2. Give one control that addresses that failure, explain how it works in the pipeline, then give the concrete benefit.
  3. For an optimisation question, name the trade-off. Faster feedback must not mean abandoning coverage, security gates, or meaningful reporting.
  4. For a tool question, distinguish configuration/environment/reporting failures from an actual vulnerability finding.

Practice question 1 - secure delivery scenario (20 marks)

Inspired by: 2024/25 Question 1 and 2025/26 Question 1.

Scenario. HealthRoute runs a web and mobile appointment service. Releases are slow because tests are mainly manual; feature branches are merged late and often conflict; staging differs from production; and a vulnerable third-party library was discovered after release. The service handles health and payment data.

(a) Recommend four specific CI/CD or DevSecOps improvements. Link each to a stated HealthRoute problem. [8 marks]

Answer route: use four distinct problems, not four names for one scanner.

Model answer:

  1. Pull-request CI: trigger build, unit and integration tests on each pull request. Developers receive feedback before merge, so defects and incompatible changes are found earlier than in manual release testing.
  2. Frequent integration with protected main: use short-lived feature branches, required review and a passing CI status before merge. This reduces long-lived divergence and makes merge conflicts smaller and easier to resolve.
  3. Staging parity and automated regression testing: deploy the same versioned artefact to a production-like staging environment and run regression/API tests there. This catches configuration and integration faults that unit tests cannot see.
  4. Security gates and release safety: run SAST and dependency/secret scanning in CI; block or explicitly risk-accept critical findings. Build a versioned image, deploy it in a controlled way, and retain a tested rollback path. This addresses late library discovery and limits the impact of a bad release.

What earns the marks: a control, the pipeline point where it operates, the named scenario failure, and the resulting benefit. “Use DevSecOps” alone earns little.

(b) Outline the key stages of a GitHub Actions pipeline that tests pull requests, builds and pushes an image after merge to main, then deploys to staging. [5 marks]

Model answer: Use a pull-request trigger for checkout, dependency installation, unit/integration tests and fast security checks. Use a push-to-main trigger only after the change is merged. In that job: checkout the exact commit; build and test; create and scan a versioned Docker image; push it to the registry; deploy that same version to staging; run a smoke test; publish status and reports. Production deployment should be a separate controlled promotion, not an accidental consequence of every commit.

(c) A junior developer runs tests only after merging to main, deploys every successful commit directly to production, and has no rollback. State two risks and two improvements. [4 marks]

Model answer: Tests only on main allow a broken feature to enter the shared branch; run required checks on pull requests and protect main. Direct production deployment can expose users to untested configuration, regression or security failures; deploy the already-tested artefact to staging first and use progressive production release. With no rollback, recovery depends on an emergency code fix; retain the previous immutable version and automate or document rollback.

(d) The vulnerable library has already reached production. Give a safe response sequence. [3 marks]

Model answer: Identify the deployed component and version from the dependency lockfile or release record, assess exploitability and exposure, then contain the risk (for example disable the affected feature or restrict access) while upgrading or applying the vendor mitigation. Rebuild, scan, regression-test and redeploy the patched version; monitor after deployment and record ownership and deadline. Do not simply update a dependency in a branch without confirming what production runs.

Practice question 2 - repeated security automation pattern (20 marks)

Inspired by: 2024/25 Question 2 and 2025/26 Question 2. SAST/DAST, OWASP ZAP, SonarQube performance and coverage all appear in both papers.

(a) Compare SAST and DAST by lifecycle timing, suitable vulnerabilities, source-code access, and one tool example each. [5 marks]

Model answer: SAST analyses source, bytecode or build artefacts without executing the running application. It runs early in development/CI and is useful for code-level patterns such as injection risks, insecure APIs, hard-coded secrets or unsafe data flow; SonarQube is an example. DAST probes a running application, normally in staging or an authorised test environment, so it can find runtime/configuration issues such as exposed endpoints, missing security headers, authentication/session weaknesses and some injection behaviour; OWASP ZAP is an example. SAST needs code or an analysable artefact; DAST does not need source code but needs a reachable, safely configured target. They complement rather than replace each other.

(b) OWASP ZAP causes the pipeline to fail and produces no useful report. Give two likely technical causes and a resolution for each. [5 marks]

Model answer:

  1. Target reachability or startup: ZAP starts before the staging service is healthy, or the runner cannot reach the target network. Add a health check/retry, expose the authorised test endpoint to the runner, and fail clearly if it is unavailable.
  2. Authentication/report configuration: the scan is unauthenticated or uses the wrong context, so it sees only a login page; alternatively the report path is not persisted. Configure test credentials/context and scope, then upload the HTML/JSON report as a pipeline artefact even when the scan finds issues.

Exam technique: name the failure mechanism, then give an operational fix. “Configure ZAP correctly” is not a diagnosis.

(c) SonarQube slows feedback. Propose two performance improvements without reducing scan quality, and give a trade-off for each. [5 marks]

Model answer:

  1. Cache dependencies and scanner data; use incremental or changed-code analysis where supported. This avoids downloading and reanalysing unchanged inputs on every run. The trade-off is cache invalidation and configuration complexity; scheduled/full scans are still needed to catch wider issues.
  2. Split fast pull-request analysis from a full main/nightly analysis, while keeping the quality gate for changed code. Developers get rapid, relevant feedback and the full scan preserves broader assurance. The trade-off is that some repository-wide findings arrive later, so ownership and reporting must make that delay visible.

(d) Coverage is low in payment logic. Explain how to use a coverage tool and give one efficient improvement strategy. [5 marks]

Model answer: Configure a tool such as JaCoCo, Istanbul or Coverage.py in the test job to produce line/branch coverage reports and publish them as build artefacts or quality-gate input. Inspect the payment package for unexecuted branches, especially error handling, authorisation decisions, rounding/limit boundaries and failure paths. Add focused unit tests around those branches using mocks or fakes for slow external gateways, then retain a smaller number of integration tests for the real boundary. This increases meaningful coverage without making every pull request wait for a large end-to-end suite.

Final check before you finish an answer

  • Have I linked every proposed control to a fact in the scenario?
  • Have I said where the control runs and what evidence it produces?
  • For SAST/DAST, have I compared rather than merely defined them?
  • For tool failures, have I supplied a cause and a practical resolution?
  • For optimisation, have I acknowledged the assurance/feedback trade-off?
