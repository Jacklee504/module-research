CT417 Revision

Secure Software Engineering and DevSecOps

Build security into decisions, code, pipeline and operations instead of treating it as a final test.

Rapid exam refresher

  • Threat model/review/dependencies/secrets/SAST/DAST/release/monitoring.
  • shift-left plus runtime.
  • SBOM/provenance.

Purpose, scope and examiner demand

Secure software engineering integrates security throughout the development lifecycle. DevSecOps makes security a shared, automated and observable delivery responsibility. It is central to CT417’s official scope and connects the CI/CD, testing and vulnerability topics.

Exam focus by part

  • Threat model/review/dependencies/secrets/SAST/DAST/release/monitoring.
  • shift-left plus runtime.
  • SBOM/provenance.

Question-demand diagnosis and answer plan

Scenarios ask how to shift security left or how to make a pipeline safer. Start with assets and abuse cases, then map controls across requirements, design, implementation, CI, deployment and operation. Explain ownership, evidence and the response path for a discovered issue.

Question-type cues

  • Application cue: Secure payment-service release with libraries.
  • Analysis cue: Critical dependency CVE after deploy.

Definitions, notation and discriminating comparisons

  • Shift left: address security earlier when change is cheaper.
  • Threat modelling: systematic reasoning about assets, attackers, entry points and mitigations.
  • Abuse case: requirement written from a malicious or misuse perspective.
  • Least privilege / defence in depth: minimum permissions / overlapping controls.
  • SBOM: software bill of materials listing components and versions.
  • Security gate: a release rule triggered by defined risk evidence.

Step-by-step methods and solution routes

  1. At requirements, identify assets, privacy/security constraints and abuse cases.
  2. At design, threat-model trust boundaries and choose authentication, authorisation, validation and logging controls.
  3. At implementation, use review, secure coding standards, secret scanning and dependency management.
  4. In CI, automate tests, SAST, dependency/container checks and policy thresholds; make findings visible to developers.
  5. Before/after deployment, use hardened configuration, least-privilege identities, DAST in approved environments, monitoring and incident response.
  6. Feed incidents and metrics back into requirements, controls and training. This closes the DevSecOps loop.

Worked examples and method extensions

Practice

A student team is adding file upload to a public service and plans to “run a security scan before release.” Improve the plan.

Model answer

First threat-model uploads: an attacker may submit malware, huge files or files disguised as images, exposing storage and downstream users. Specify allowed types, size limits, authentication and retention. At design, store uploads outside the web root with a generated name and least-privilege service identity. In implementation, validate content and metadata, never trust the client filename, and review code. In CI run unit/integration tests, SAST and dependency checks; scan the built container and produce an SBOM. In staging, run permitted DAST and test upload abuse cases. In production monitor failures and quarantine events, patch dependencies, and use an incident runbook. A final scan alone is too late and cannot replace design controls.

Graded practice and hard extensions

1. Foundation

What does “shift left” mean, and why is it not “security belongs only to developers”?

Answer check: it means earlier feedback and design decisions, while operations, security specialists and product owners still share responsibility.

2. Exam bridge

Design a DevSecOps control map for a service that handles student records.

Answer check: cover requirements/privacy, threat model and access design, reviews/scans/tests, protected deployment/secrets, monitoring/audit/incident response, evidence and feedback. Relate controls to sensitive data.

Hard practice — question demand

Critical dependency CVE after deploy.

Plan / choice of method

Model the failure or boundary first, then apply these page-specific concepts in order: Threat model/review/dependencies/secrets/SAST/DAST/release/monitoring.; shift-left plus runtime.; SBOM/provenance. Finish by checking the final state against the deadline, security property, consistency contract, or performance requirement.

Worked answer

Assess exposure, contain/mitigate or upgrade, rebuild/sign/promote, regression-test/monitor and track SBOM/patch SLA with owned exception.

Mark-winning points

Credit requires the complete method sequence, explicit verification of the conclusion, and the limiting assumption/trade-off—not merely the recommended technology.

Common trap

Blocking every low-risk warning without triage, thereby encouraging bypasses.

Topic-specific traps and diagnosis

  • Equating DevSecOps with installing one scanner.
  • Putting secrets in a repository or logs.
  • Ignoring authorisation, audit and recovery while discussing encryption.
  • Blocking every low-risk warning without triage, thereby encouraging bypasses.

Exam marking checklist

  • Map controls across the lifecycle.
  • Name assets, threats/trust boundaries and responsible roles.
  • Include automated evidence plus operational monitoring.
  • Explain how findings are fixed and learned from.
