CT417 Revision

CI/CD and Git Workflows

Turn a fragile release process into a safe, repeatable delivery pipeline.

Rapid exam refresher

  • CI integrates/test changes.
  • CD promotes immutable artifact.
  • conflicts are divergent edits.
  • cue: revision→build/test/scan→digest→deploy→verify/rollback.

Purpose, scope and examiner demand

Continuous integration (CI) frequently merges small changes and automatically builds and tests them. Continuous delivery/deployment (CD) carries a verified artefact towards production, with delivery retaining an approval and deployment automating the final release. Git workflows make those changes reviewable and recoverable. These are high-value recent CT417 scenario skills.

Exam focus by part

  • CI integrates/test changes.
  • CD promotes immutable artifact.
  • conflicts are divergent edits.
  • cue: revision→build/test/scan→digest→deploy→verify/rollback.

Question-demand diagnosis and answer plan

A scenario usually asks why builds fail, how to improve a pipeline, or how a team should recover from branches and conflicts. Answer in this order: diagnose the risk; give the Git or pipeline sequence; name checks and artefacts; explain rollback/approval; state one trade-off.

Question-type cues

  • Application cue: Pipeline cannot pull app:latest.
  • Analysis cue: Frequent feature branches destabilise production.

Definitions, notation and discriminating comparisons

  • Repository, working tree, staging area, commit: stored project, local files, selected change set, recorded snapshot.
  • Branch, merge, rebase, pull request (PR): parallel line, combine histories, replay commits, reviewed change proposal.
  • Trigger, job, runner, artefact: event, grouped steps, machine that executes them, versioned build output.
  • Pipeline: checkout → build → test → scan → package → deploy → monitor/rollback.

Step-by-step methods and solution routes

  1. Create a short-lived feature branch from the current main branch.
  2. Make coherent commits, push, and open a PR. Inspect CI feedback and review before merging.
  3. On push/PR, run checkout, dependency setup, build, unit tests, coverage and security/quality checks.
  4. Package one immutable, versioned artefact or container image. Promote that same artefact through staging and production.
  5. Use environment secrets, deployment gates and health checks. If the release fails, roll back to the known-good version and investigate.

Worked examples and method extensions

Practice

A team deploys directly from laptops. A hotfix overwrites another change and production differs from test. Propose a safer workflow.

Model answer

Use protected main and short feature branches. Each change is pushed to a PR, where a GitHub Actions workflow checks out the revision, builds it, runs tests and quality/security scans. Merge only after review and green checks. Build a tagged image once, deploy that exact image to staging, run a smoke test, then require approval for production. Store credentials as secrets and retain the previous image tag so failed health checks can roll back. This removes laptop-only state and makes the released revision traceable.

Graded practice and hard extensions

1. Foundation

Distinguish CI, continuous delivery and continuous deployment.

Answer check: CI integrates and verifies changes; delivery keeps a deployable release with a human release decision; deployment automates release after checks.

2. Exam bridge

Sketch a GitHub Actions pipeline for a web service and justify where tests, scans, image publishing and deployment belong.

Answer check: include trigger, checkout, setup/build, fast tests before expensive scans, versioned image after checks, staging/health gate, production approval or automated release, plus rollback.

Hard practice — question demand

Frequent feature branches destabilise production.

Plan / choice of method

Model the failure or boundary first, then apply these page-specific concepts in order: CI integrates/test changes.; CD promotes immutable artifact.; conflicts are divergent edits. Finish by checking the final state against the deadline, security property, consistency contract, or performance requirement.

Worked answer

Protected PRs, small/frequent integration, tests/scans, staging promotion, monitored rollout and rollback—not rebuilding latest per environment.

Mark-winning points

Credit requires the complete method sequence, explicit verification of the conclusion, and the limiting assumption/trade-off—not merely the recommended technology.

Common trap

Putting secrets in YAML or source control.

Topic-specific traps and diagnosis

  • Calling a pipeline “CI/CD” without describing triggers, checks or promotion.
  • Confusing pull with a PR, or treating a merge conflict as a Git error rather than competing edits requiring a decision.
  • Rebuilding separately per environment instead of promoting one artefact.
  • Putting secrets in YAML or source control.

Exam marking checklist

  • Define CI and distinguish the two CD meanings.
  • Give a concrete Git sequence and a pipeline sequence.
  • Include quality gates, immutable artefacts, environment protection and rollback.
  • Connect each recommendation to a scenario risk.
