CT4108 Revision

HPC, Storage and Large Data

Match a large-data workload to parallel compute, storage placement and movement constraints.

Rapid exam refresher

  • Profile compute/memory/network/I/O.
  • parallel storage striping/metadata matter.
  • Amdahl limits speedup.
  • cue: quantify bottleneck.

Purpose, scope and examiner demand

High-performance computing (HPC) combines resources to solve large computations quickly. Large-data systems must also store, move and recover data efficiently; compute speed alone cannot fix an I/O bottleneck.

Exam focus by part

  • Profile compute/memory/network/I/O.
  • parallel storage striping/metadata matter.
  • Amdahl limits speedup.
  • cue: quantify bottleneck.

Question-demand diagnosis and answer plan

  1. Characterise data size, access pattern and operation.
  2. Split work and data into partitions.
  3. Place computation near data where possible and describe aggregation.
  4. Evaluate bottlenecks: I/O, network, skew, memory, failure or coordination.

Question-type cues

  • Application cue: 10% serial work, 16 processors.
  • Analysis cue: More nodes slow pipeline.

Definitions, notation and discriminating comparisons

  • Throughput: work completed per time; latency: time for one operation.
  • Partitioning: divide data/work among workers; data locality: process near stored data.
  • Parallel speedup: serial time divided by parallel time; real speedup is limited by serial work and overhead.
  • Data skew: uneven partition sizes make some workers stragglers.
  • Checkpoint: saved state used to recover after a fault.

Step-by-step methods and solution routes

Estimate which resource dominates. Partition a log by time or key, assign partitions to workers, compute local results, then combine them. Check whether one popular key produces a huge partition. Add replicated storage or checkpoints for faults, but explain the extra storage and communication cost.

Reasoning checkpoints

  1. Use and justify: Profile compute/memory/network/I/O.
  2. Use and justify: parallel storage striping/metadata matter.
  3. Use and justify: Amdahl limits speedup.
  4. Use and justify: cue: quantify bottleneck.

Worked examples and method extensions

To count events in a 1 TB log, split files across workers. Each worker counts locally; a final stage adds the counts. If all records for one customer key go to one worker, that worker delays completion: use a better partition key or split that hot key before aggregation.

Exam-paper-led practice

Practice question 1 [medium/hard]

Scenario and demand: A job is 10% serial and 90% perfectly parallel. Compute Amdahl’s ideal speedup at 16 processors and explain why 16× is impossible. [8 marks]

Question-demand diagnosis and fastest route: S(16)=1/(0.10+0.90/16)=1/0.15625=6.4. The serial fraction caps asymptotic speedup at 10, even before communication, synchronisation and I/O. Profile first: reducing the serial coordinator or overlapping I/O can improve the bound; adding processors to a fixed serial phase cannot. Trap: using 0.9×16=14.4 ignores serial elapsed time.

Practice question 2 [medium/hard]

Scenario and demand: Adding nodes makes a data pipeline slower. Give a measurement-led diagnosis across compute, memory, network and parallel storage. [9 marks]

Question-demand diagnosis and fastest route: Measure CPU utilisation, memory bandwidth/cache misses, network shuffle time, metadata operations and read/write throughput per node. Small-file metadata contention or poorly striped shared output can dominate despite spare CPU. Combine large files/collective I/O, choose an appropriate stripe count, batch metadata operations and avoid all workers contending for one writer. Validate by comparing phase timings before/after, not node count alone. Trap: maximum disk bandwidth is irrelevant if metadata or network is the bottleneck.

Topic-specific traps and diagnosis

  • Claiming linear speedup without accounting for overhead.
  • Choosing partitions without considering skew or locality.
  • Confusing storage capacity with read/write throughput.

Exam marking checklist

  • Did I map data and work to resources?
  • Did I identify the aggregation and bottleneck?
  • Did I mention fault/recovery consequences?
