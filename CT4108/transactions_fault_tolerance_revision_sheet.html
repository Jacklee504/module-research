CT4108 Revision

Transactions and Fault Tolerance

Keep related state changes coherent, then explain how the design responds when a component fails.

Rapid exam refresher

  • ACID: atomicity, consistency, isolation, durability.
  • 2PC logs prepare votes and commits only all-yes, but prepared participants can block after coordinator failure.
  • Sagas use local transactions and compensations: higher availability, weaker isolation.
  • Use durable state, idempotency, timeout/retry and clear terminal outcome.

Paper evidence and scope

No CT4108 papers: syllabus-based.

Medium practice — 15 marks

Booking reserves seat then charges card. (a) [5] 2PC vs saga. (b) [5] saga design. (c) [5] duplicate request.

Answers

(a): 2PC offers atomic decision but blocks; saga fits long-lived external work. Trap: calling compensation a database rollback.

(b): reserve→charge→confirm; compensate release/refund on later failure, persist transitions. Trap: no compensation path.

(c): idempotency key/result stored before reply; repeats return outcome. Trap: retry causes second charge.

Hard practice — 15 marks

Coordinator crashes after prepared yes votes. (a) [5] state. (b) [5] recovery. (c) [5] trade-off.

Answers

(a): participant is in-doubt and retains locks/log. (b): recover durable decision or query protocol peers/coordinator. (c): atomicity can cost availability; replicated coordinator/consensus adds coordination. Trap: participant guesses commit.
