CT4108 Revision

Transactions and Fault Tolerance

Keep related state changes coherent, then explain how the design responds when a component fails.

Rapid exam refresher

  • ACID and isolation.
  • 2PC durable prepare then decision but blocks.
  • checkpoint is backward recovery.
  • logs/idempotence enable retry.

Purpose, scope and examiner demand

A transaction groups operations into a meaningful unit. Fault tolerance preserves an agreed service property despite specified faults; it does not mean that every request succeeds during every outage.

Exam focus by part

  • ACID and isolation.
  • 2PC durable prepare then decision but blocks.
  • checkpoint is backward recovery.
  • logs/idempotence enable retry.

Question-demand diagnosis and answer plan

  1. State the business invariant and operations.
  2. Identify transaction participants and commit decision.
  3. Trace a crash or lost message.
  4. Explain recovery, retries, logging, compensation or degraded outcome.

Question-type cues

  • Application cue: Coordinator dies after all 2PC yes votes.
  • Analysis cue: Crash during transfer then client retries.

Definitions, notation and discriminating comparisons

  • Atomicity: all intended transaction effects occur or none do.
  • Commit: make a decision durable; abort: discard/undo the unit.
  • Two-phase commit (2PC): coordinator asks participants to prepare, then decides commit/abort.
  • Write-ahead log: durable record written before relying on a state update.
  • Compensation: later business action that offsets an already completed action.

Step-by-step methods and solution routes

First state the invariant, for example “money is neither created nor lost.” In 2PC, participants record readiness before voting yes; the coordinator records the final decision before notifying them. If a participant crashes, recovery reads its log. Mention the cost: prepared participants can wait if the coordinator is unavailable.

Reasoning checkpoints

  1. Use and justify: ACID and isolation.
  2. Use and justify: 2PC durable prepare then decision but blocks.
  3. Use and justify: checkpoint is backward recovery.
  4. Use and justify: logs/idempotence enable retry.

Worked examples and method extensions

A transfer debits A by €20 and credits B by €20. The coordinator asks both databases to prepare, then records and broadcasts commit only if both can commit. If B cannot prepare, it aborts and A does not debit. If the coordinator fails after prepare, participants consult recovery/decision information rather than guessing.

Exam-paper-led practice

Practice question 1 [medium/hard]

Scenario and demand: In 2PC, all participants have durably voted YES and the coordinator crashes before sending its decision. Explain the states, recovery evidence and blocking risk. [9 marks]

Question-demand diagnosis and fastest route: Each participant has logged PREPARED and holds locks after YES; it cannot unilaterally abort because another participant may have committed. On recovery the coordinator reads its durable log: a logged decision is retransmitted; no decision requires the protocol’s safe recovery path/coordination. This is why 2PC can block under coordinator failure despite atomicity. Trap: a YES vote is not a commit decision.

Practice question 2 [medium/hard]

Scenario and demand: A transfer debits A then the service crashes before crediting B; the client retries. Give a transactional recovery design. [8 marks]

Question-demand diagnosis and fastest route: Use one ACID transaction where possible: log intent and both updates, commit atomically, then return a durable transaction ID. Recovery redoes committed work or undoes incomplete work from the write-ahead log; retry with the same ID returns the recorded result. In distributed settings, a saga/compensation must be explicit and idempotent. Trap: a checkpoint is recovery from a known state, not evidence that an external side effect was never made.

Topic-specific traps and diagnosis

  • Calling compensation a perfect rollback.
  • Omitting the invariant being protected.
  • Claiming 2PC removes all failures or availability cost.

Exam marking checklist

  • Did I cover a specific failure and recovery?
  • Did I state a limitation/trade-off?
