CT4108 Revision

Distributed Algorithms

Describe an algorithm through its local actions, messages, assumptions and system-wide property.

Rapid exam refresher

  • Consensus needs agreement/validity/termination under named failures.
  • election unique leader.
  • Lamport one-way causality, vectors reveal concurrency.

Purpose, scope and examiner demand

A distributed algorithm reaches a global outcome using only local state and communication. In an answer, state exactly what is guaranteed—such as election of one leader—not merely that nodes “agree.”

Exam focus by part

  • Consensus needs agreement/validity/termination under named failures.
  • election unique leader.
  • Lamport one-way causality, vectors reveal concurrency.

Question-demand diagnosis and answer plan

  1. State nodes, topology and assumptions (IDs, reliable links, failures).
  2. Define local state and messages.
  3. Walk through the rule each node follows.
  4. Argue safety, progress and message-cost intuition.

Question-type cues

  • Application cue: Compare Lamport and vector clocks.
  • Analysis cue: Leader dies during coordination.

Definitions, notation and discriminating comparisons

  • Safety: a bad thing never happens; liveness: a required good thing eventually happens.
  • Leader election: selecting one coordinator from participating nodes.
  • Termination: nodes know the algorithm is complete.
  • Topology: communication structure, for example a ring.
  • Asynchronous: no known upper bound on message delay or process speed.

Step-by-step methods and solution routes

Turn the specification into invariants. For election, require at most one elected leader (safety) and eventually an election if the assumptions hold (liveness). Trace messages for a small network. Finally identify where the proof relies on unique IDs, reliable delivery or no failures.

Reasoning checkpoints

  1. Use and justify: Consensus needs agreement/validity/termination under named failures.
  2. Use and justify: election unique leader.
  3. Use and justify: Lamport one-way causality, vectors reveal concurrency.

Worked examples and method extensions

Three ring nodes have IDs 4, 9 and 6. Each sends its ID around the ring and forwards only the largest ID seen. ID 9 returns to node 9, so it declares itself leader and announces this. Safety depends on IDs being unique; progress depends on the ring forwarding messages.

Exam-paper-led practice

Practice question 1 [medium/hard]

Scenario and demand: Processes A and B send to C; A’s event a happens-before its send, and C receives A’s message before sending to B. Compare Lamport and vector clocks for deciding whether a concurrent B event caused C’s send. [9 marks]

Question-demand diagnosis and fastest route: Lamport clocks increment locally and set receive time above the carried value, so L(a)<L(C-send) establishes an order but the converse does not establish causality: ordered scalar values can be concurrent. A vector clock increments its own component and merges component-wise on receive. If V(B-event) and V(C-send) are incomparable (each has a greater component), they are concurrent; if every component of B is ≤ C and one is strict, B happened-before C. Trap: a smaller Lamport timestamp is not proof of causality.

Practice question 2 [medium/hard]

Scenario and demand: A leader crashes after proposing a commit to replicas. State the consensus properties and a safe response under partial failure. [8 marks]

Question-demand diagnosis and fastest route: Agreement means no two correct replicas decide differently; validity constrains decisions to proposed values; termination is conditional on the failure/timing model. A timeout gives suspicion, not proof of crash, so surviving replicas use a quorum/election protocol and durable log to select a leader that preserves the highest safe proposal before deciding. Never let two isolated groups each commit a different value. Trap: calling a timeout a failure detector with perfect knowledge.
