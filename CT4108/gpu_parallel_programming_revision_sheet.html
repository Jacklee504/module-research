CT4108 Revision

GPU and Parallel Programming

Break a computation into safe independent work while accounting for data movement and synchronisation.

Rapid exam refresher

  • Threads/blocks/grid map data.
  • coalescing/shared memory improve throughput.
  • divergence/races hurt.
  • barriers have scope.

Purpose, scope and examiner demand

GPU programming uses many lightweight workers to perform similar operations on different data. The key question is whether iterations are independent enough to run concurrently and whether memory transfer overwhelms the gain.

Exam focus by part

  • Threads/blocks/grid map data.
  • coalescing/shared memory improve throughput.
  • divergence/races hurt.
  • barriers have scope.

Question-demand diagnosis and answer plan

  1. Identify the data-parallel operation and output for each index.
  2. Map indices to threads/work-items and groups/blocks conceptually.
  3. Explain memory reads/writes and any required barrier or reduction.
  4. Discuss parallelism, overhead, divergence and transfer cost.

Question-type cues

  • Application cue: Launch CUDA-style vector addition for n=1000 elements with blockDim.x=256. Give kernel pseudocode, grid size, the last valid thread index, and the purpose of the bounds guard.
  • Analysis cue: Sum n=1024 floats using blockDim.x=256. Specify the two-stage reduction, shared-memory indexing, synchronisation points, and final number of partial sums.

Definitions, notation and discriminating comparisons

  • Kernel: function launched across many GPU workers.
  • Thread/work-item: one logical execution instance; block/work-group: cooperating collection.
  • SIMT: many threads execute a common instruction stream conceptually.
  • Coalesced access: neighbouring workers access nearby memory efficiently.
  • Reduction: combine many values, for example a sum, into one.

Step-by-step methods and solution routes

Express the serial loop as output[i]=f(input[i]) where possible. Allocate/copy input, launch one worker per valid i, bounds-check i, then copy output back if required. For a sum, use partial sums and synchronisation rather than letting all workers write one shared accumulator unsafely.

  4. Use and justify: barriers have scope.

Worked examples and method extensions

To add arrays A and B of length n, worker i computes C[i]=A[i]+B[i] when i<n. Each worker writes a distinct C[i], so no lock is needed. The design is less effective if n is tiny or host-to-device copying dominates the arithmetic.

Medium practice — question demand

Launch CUDA-style vector addition for n=1000 elements with blockDim.x=256. Give kernel pseudocode, grid size, the last valid thread index, and the purpose of the bounds guard.

Plan / choice of method

Use one thread per vector element with i=blockIdx.x·blockDim.x+threadIdx.x. Compute gridDim.x=⌈n/blockDim.x⌉, then solve the index equation for i=999 to identify the last useful thread. Check that surplus threads fail i<n before accessing memory.

Worked answer

kernel add(a,b,c,n) { i = blockIdx.x * blockDim.x + threadIdx.x; if (i < n) c[i] = a[i] + b[i]; } Launch ⌈1000/256⌉=4 blocks, creating 1024 threads. Index 999 is blockIdx.x=⌊999/256⌋=3 and threadIdx.x=999−3·256=231. In the last block, threads 232–255 map to indices 1000–1023 and must return at the i<n guard. Adjacent threads read adjacent a/b elements and write adjacent c elements, so accesses are coalesced; no barrier is needed because outputs are independent.

Mark-winning points

Credit requires the named mechanism, all intermediate values or protocol states, the final conclusion, and these topic checks: Threads/blocks/grid map data.; coalescing/shared memory improve throughput.; divergence/races hurt.; barriers have scope.

Common trap

Launching only three blocks, or omitting i<n and allowing the last 24 threads to access beyond the arrays.

Graded practice and hard extensions

Prompt 1 — 7 marks

Turn vector addition into a GPU kernel plan. Check: give index mapping, bounds check, distinct outputs and data-transfer note.

Prompt 2 — 8 marks

Explain why summing an array needs more care than vector addition. Check: identify the shared accumulator race and outline a staged reduction/barrier.

Hard practice — question demand

Sum n=1024 floats using blockDim.x=256. Specify the two-stage reduction, shared-memory indexing, synchronisation points, and final number of partial sums.

Plan / choice of method

Launch four blocks. Each thread loads one input into shared memory s[tid]. After a block barrier, halve stride from 128 to 1; when tid<stride, add s[tid+stride] into s[tid], followed by a barrier at every stride. Write one sum per block, then reduce the four partial sums with one block or on the host.

Worked answer

i=blockIdx.x*256+tid; s[tid]=(i<n?x[i]:0); sync(); for(stride=128; stride>0; stride/=2){ if(tid<stride) s[tid]+=s[tid+stride]; sync(); } if(tid==0) partial[blockIdx.x]=s[0]; Four first-stage blocks produce partial[0..3]. A second kernel with one block loads those four values (zeros for other lanes) and repeats the tree, producing one total. The barriers ensure every stride reads completed writes; independent block sums avoid a cross-block barrier that the kernel cannot provide.

Mark-winning points

Credit requires the complete method sequence, explicit verification of the conclusion, and the limiting assumption/trade-off—not merely the recommended technology.

Common trap

Updating one global total non-atomically, or assuming a block barrier synchronises different blocks.

Topic-specific traps and diagnosis

  • Assuming every loop is safe to parallelise.
  • Ignoring host/device transfer and launch overhead.
  • Writing the same output location from many threads without coordination.

Exam marking checklist

  • Can I state the work for index i?
  • Did I identify dependencies and synchronisation?
  • Did I discuss a performance limitation?
