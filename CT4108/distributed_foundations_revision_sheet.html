CT4108 Revision

Distributed Foundations

Build a precise picture of why a distributed system is different from one program on one machine.

Rapid exam refresher

  • No global clock and partial failures.
  • timeout is suspicion.
  • safety differs from liveness.
  • retries need IDs/idempotence.

Purpose, scope and examiner demand

A distributed system coordinates independent computers through a network to provide a service. Good answers connect its benefits to its new problems: no shared clock, partial failure and network delay.

Exam focus by part

  • No global clock and partial failures.
  • timeout is suspicion.
  • safety differs from liveness.
  • retries need IDs/idempotence.

Question-demand diagnosis and answer plan

  1. Name the components and the service they jointly provide.
  2. State the communication and failure assumptions.
  3. Explain one benefit and one distributed-system difficulty.
  4. Finish with a mechanism that manages that difficulty.

Question-type cues

  • Application cue: Why is silence not proof of crash?
  • Analysis cue: Duplicates and inconsistent reads follow retry.

Definitions, notation and discriminating comparisons

  • Node: an independent computer; process: executing program on a node.
  • Network partition: nodes cannot communicate though some may still run.
  • Partial failure: one component fails while others continue.
  • Scalability: retaining useful performance as load or nodes grow.
  • Transparency: hiding distribution where practical, without pretending failures cannot happen.

Step-by-step methods and solution routes

Start with the service boundary. Then identify who holds data, who sends requests and what happens if a message is delayed or a node stops. Choose a timeout, retry, replication or graceful error according to the requirement. State its limit: a timeout cannot prove a remote node has failed.

Reasoning checkpoints

  1. Use and justify: No global clock and partial failures.
  2. Use and justify: timeout is suspicion.
  3. Use and justify: safety differs from liveness.
  4. Use and justify: retries need IDs/idempotence.

Worked examples and method extensions

A photo service stores files on two servers. A client uploads to server A; A copies to B. This can improve availability if A later crashes, but copying needs network messages and the two copies may briefly differ. The design must decide whether the client waits for both copies or accepts a later update.

Medium practice — question demand

Why is silence not proof of crash?

Plan / choice of method

Select the governing concepts before calculating: No global clock and partial failures.; timeout is suspicion.; safety differs from liveness. Apply them only under the assumptions stated in the question, and compare the result with the required condition.

Worked answer

Delay, partition, pause and crash are indistinguishable asynchronously; use bounded retry/health/quorum policy while accepting false suspicion or delay.

Mark-winning points

Credit requires the named mechanism, all intermediate values or protocol states, the final conclusion, and these topic checks: No global clock and partial failures.; timeout is suspicion.; safety differs from liveness.; retries need IDs/idempotence.

Common trap

Ignoring data placement and partial failure.

Graded practice and hard extensions

Prompt 1 — 6 marks

Explain why partial failure makes a distributed service harder than a single-machine service. Check: name delay, uncertainty and an operational response (timeout/retry).

Prompt 2 — 8 marks

Sketch a scalable document service with two nodes. Check: identify roles, a benefit, a failure case and a limitation of your mitigation.

Hard practice — question demand

Duplicates and inconsistent reads follow retry.

Plan / choice of method

Model the failure or boundary first, then apply these page-specific concepts in order: No global clock and partial failures.; timeout is suspicion.; safety differs from liveness. Finish by checking the final state against the deadline, security property, consistency contract, or performance requirement.

Worked answer

Use durable operation IDs/dedup/outbox, idempotent handlers, versions and declared consistency/quorum policy; partitions force trade-off.

Mark-winning points

Credit requires the complete method sequence, explicit verification of the conclusion, and the limiting assumption/trade-off—not merely the recommended technology.

Common trap

Ignoring data placement and partial failure.

Topic-specific traps and diagnosis

  • Equating “networked” with automatically scalable or reliable.
  • Saying a timeout proves a node failed.
  • Ignoring data placement and partial failure.

Exam marking checklist

  • Did I state components, communication and failure assumptions?
  • Did I balance benefit with trade-off?
  • Did I explain a concrete mechanism?
