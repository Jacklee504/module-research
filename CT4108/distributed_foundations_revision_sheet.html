CT4108 Revision

Distributed Foundations

Build a precise picture of why a distributed system is different from one program on one machine.

Rapid exam refresher

  • Components fail independently; network delay/loss and no global clock make partial failure normal.
  • Specify safety, liveness, failure model and assumptions; transparency has coordination cost.
  • Scalability needs bounded coordination, partitioning, caching and backpressure; distinguish throughput from latency.

Paper evidence and scope

No local CT4108 papers exist: all practice is syllabus-based.

Medium practice — 15 marks

A two-region photo service has API, object store and metadata DB. (a) [5] identify failed assumptions. (b) [5] resilience boundary. (c) [5] safety/liveness properties.

Answer for every part

(a) Route: partial failure/no global time/unreliable link. Answer: API may run while DB is unreachable; messages may delay/duplicate; clocks disagree. Trap: assuming timeout proves failure.

(b) Route: define degraded behaviour. Answer: use timeouts, idempotent upload IDs and explicit pending/final outcome. Trap: retrying non-idempotent writes blindly.

(c) Route: state one ‘never’ and one ‘eventually’. Answer: never cross-tenant disclose; accepted upload eventually becomes visible or terminal failure. Trap: promising progress during permanent partition.

Hard practice — 15 marks

“Hide every failure from users.” (a) [5] critique. (b) [5] API design. (c) [5] observability.

Answer for every part

(a) Answer: retries can hide transients but add delay/duplicates; partition trade-offs remain. Trap: claiming transparency erases physics.

(b) Answer: return operation ID/status and make create idempotent. Trap: synchronous infinite wait.

(c) Answer: correlation IDs, retry/queue metrics and traces distinguish slow from failed dependency. Trap: logs without request linkage.
