CT420 Revision

QUIC, HTTP/2 and HTTP/3

Explain the protocol stack and relate each design choice to a performance problem.

Rapid exam refresher

  • HTTP/2 binary frames, multiplexing and header compression address HTTP/1 limits, but TCP HOL remains.
  • QUIC integrates TLS 1.3, streams, loss recovery and connection IDs; HTTP/3 maps HTTP to streams.
  • Stream loss isolation is not unlimited capacity; 0-RTT has replay risk.

Paper evidence and scope

QUIC establishment 2023/24 and HTTP/2 features 2024/25; adapted practice.

Medium practice — 15 marks

Lossy mobile page. (a) [5] HTTP/1→2. (b) [5] HTTP/3. (c) [5] 0-RTT.

Answers

(a): HTTP/2 multiplexes but TCP loss stalls connection. (b): QUIC other streams continue. (c): only idempotent early data. Trap: QUIC removes loss.

Hard practice — 15 marks

At 0ms a repeat client sends 0-RTT GET /catalog; at 5ms it opens streams 4=image and 8=checkout. Packet carrying stream-4 data is lost at 20ms. (a) [5] trace effect. (b) [5] decide whether 0-RTT POST /pay is safe. (c) [5] explain migration from Wi-Fi to LTE at 40ms.

Answer for every part

(a) Demand / route / worked answer / trap

Route: separate stream from connection. Answer: stream 4 waits for retransmission; stream 8 can deliver its independent frames, subject to shared congestion window. Credit: loss isolation 2, retransmit 1, congestion qualification 2. Trap: claiming every stream continues at full rate.

(b)

Route: test replay safety. Answer: GET is normally safe/idempotent; POST /pay can be replayed and must wait for 1-RTT or use explicit idempotency/anti-replay semantics. Trap: 0-RTT means encrypted therefore safe.

(c)

Route: identify CID/path validation. Answer: connection ID lets QUIC retain connection state across address change; endpoint validates new path and applies anti-amplification/congestion response. Application authentication does not change. Trap: CID identifies the user.
