QUIC, HTTP/2 and HTTP/3

Explain the protocol stack and relate each design choice to a performance problem.

Rapid exam refresher

  • HTTP/2 multiplexes but TCP HOL.
  • QUIC streams/TLS/loss/congestion, HTTP/3.
  • 0-RTT replay caveat.

Purpose, scope and examiner demand

Recent material asks why modern web transports improve setup, multiplexing and recovery. Avoid feature lists: make a cause-and-effect comparison.

Exam focus by part

  • HTTP/2 multiplexes but TCP HOL.
  • QUIC streams/TLS/loss/congestion, HTTP/3.
  • 0-RTT replay caveat.

Question-demand diagnosis and answer plan

  1. Identify the comparison: HTTP/1.1, HTTP/2 over TCP, or HTTP/3 over QUIC/UDP.
  2. State the performance symptom: connection setup, head-of-line blocking, loss recovery, or mobility.
  3. Name the responsible layer and mechanism.
  4. Give one limitation or operational trade-off.

Question-type cues

  • Application cue: Compare QUIC and TCP+TLS establishment.
  • Analysis cue: Why streams help soft real-time?

Definitions, notation and discriminating comparisons

  • Multiplexing: concurrent logical streams on one connection.
  • Head-of-line (HOL) blocking: a blocked item holds up later items. TCP's ordered byte stream can expose transport-level HOL after loss.
  • QUIC: encrypted transport over UDP with streams, loss recovery and congestion control; HTTP/3 uses QUIC.
  • 0-RTT/1-RTT: resumption/handshake opportunities that can reduce setup delay; 0-RTT has replay considerations.

Step-by-step methods and solution routes

A page has independent image and script requests. HTTP/2 multiplexes streams, so application requests need not wait serially, but a lost TCP packet can delay delivery of later bytes for all streams. HTTP/3 uses independent QUIC streams: loss on one stream need not block delivery on another stream. This can improve perceived page progress on lossy paths, while congestion control still protects the network.

Worked examples and method extensions

Question

Why can HTTP/3 reduce head-of-line blocking compared with HTTP/2?

Model answer

HTTP/2 multiplexes application streams over one TCP byte stream. TCP requires in-order delivery, so loss can delay later data even when it belongs to another HTTP/2 stream. HTTP/3 runs over QUIC, whose streams can make progress independently after loss. It reduces this transport-level HOL effect; it does not remove application dependencies or congestion limits.

Plan / choice of method

Graded practice and hard extensions

Prompt 1 - 8 marks

Compare HTTP/1.1, HTTP/2 and HTTP/3 for a busy web page. Exam bridge: connection/serial behaviour (2), HTTP/2 multiplexing (2), QUIC streams/HOL (3), balanced conclusion (1). Check: HTTP/3 is HTTP over QUIC, not simply UDP with no reliability.

Prompt 2 - 6 marks

Explain QUIC connection establishment and a 0-RTT caveat. Exam bridge: handshake purpose (2), resumption benefit (2), replay/appropriate-use caveat (2). Check: never claim 0-RTT is universally safe.

Hard practice — question demand

Why streams help soft real-time?

Plan / choice of method

Model the failure or boundary first, then apply these page-specific concepts in order: HTTP/2 multiplexes but TCP HOL.; QUIC streams/TLS/loss/congestion, HTTP/3.; 0-RTT replay caveat. Finish by checking the final state against the deadline, security property, consistency contract, or performance requirement.

Worked answer

Loss in one stream need not block others, but shared congestion remains; use priorities/telemetry, no claim of losslessness.

Mark-winning points

Credit requires the complete method sequence, explicit verification of the conclusion, and the limiting assumption/trade-off—not merely the recommended technology.

Common trap

Ignoring encryption, congestion control, and deployment trade-offs.

Topic-specific traps and diagnosis

  • Saying UDP itself guarantees QUIC's reliability or security.
  • Claiming HTTP/2 removes every form of HOL blocking.
  • Ignoring encryption, congestion control, and deployment trade-offs.
