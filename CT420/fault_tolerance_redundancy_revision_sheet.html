Fault Tolerance and Redundancy

Use the older fault-tolerance material as a principled background topic, with cautious scope.

Rapid exam refresher

  • Fault→error→failure.
  • spatial/temporal/design redundancy needs independence.
  • rollback checkpoint/backward vs forward recovery.
  • cost matters.

Purpose, scope and examiner demand

Fault tolerance keeps a service safe or available despite faults. A strong answer distinguishes detecting an error, masking it, recovering, and preventing a common-mode failure.

Exam focus by part

  • Fault→error→failure.
  • spatial/temporal/design redundancy needs independence.
  • rollback checkpoint/backward vs forward recovery.
  • cost matters.

Question-demand diagnosis and answer plan

  1. Identify the fault model: crash, bit error, component failure, or software exception.
  2. State the required property: safety, availability, integrity, or graceful degradation.
  3. Choose detection, redundancy, voting, recovery or a combination.
  4. Explain the remaining failure mode, especially a shared cause.

Question-type cues

  • Application cue: Compare checkpoint rollback and N-version voting.
  • Analysis cue: Replicas fail together.

Definitions, notation and discriminating comparisons

  • Fault: cause; error: incorrect state; failure: externally visible service deviation.
  • Spatial redundancy: parallel components; temporal redundancy: retry/recompute.
  • N-modular redundancy: multiple replicas and a voter; a voter itself can be a critical component.
  • RAID uses disk redundancy; Hamming/SEC detects/corrects certain bit errors. These are mechanisms, not universal availability guarantees.

Step-by-step methods and solution routes

For three independent sensor computations, run three replicas and majority-vote their outputs. If one replica produces a wrong value and the other two agree, the voter masks that single fault. This argument depends on independence and an adequate voter; a common software bug or shared power loss can defeat all replicas. Add diversity, monitoring or separate power where the risk requires it.

Worked examples and method extensions

Question

Explain the difference between error detection and error masking using memory and a replicated controller.

Model answer

A parity or Hamming-style code can detect (and, for suitable codes, correct) limited memory bit errors; it identifies or repairs corrupted state. Triple modular redundancy masks a single discrepant controller output through majority voting, so the external service can remain correct. Both have assumptions and coverage limits, and neither protects automatically against every common-mode fault.

Medium practice — question demand

Compare checkpoint rollback and N-version voting.

Plan / choice of method

Select the governing concepts before calculating: Fault→error→failure.; spatial/temporal/design redundancy needs independence.; rollback checkpoint/backward vs forward recovery. Apply them only under the assumptions stated in the question, and compare the result with the required condition.

Worked answer

Rollback restores state but repeats deterministic fault/time; voting masks one divergent version only if independence/voter holds; bound recovery to deadline.

Mark-winning points

Credit requires the named mechanism, all intermediate values or protocol states, the final conclusion, and these topic checks: Fault→error→failure.; spatial/temporal/design redundancy needs independence.; rollback checkpoint/backward vs forward recovery.; cost matters.

Common trap

Claiming every Hamming/RAID configuration has the same correction ability.

Graded practice and hard extensions

Prompt 1 - 8 marks

Design fault tolerance for a safety-relevant controller. Exam bridge: fault model/property (2), detection (2), redundancy/voting or recovery (3), residual risk (1). Check: distinguish a fault from its visible failure.

Prompt 2 - 6 marks

Compare RAID, Hamming/SEC and replicated voting. Exam bridge: mechanism/purpose for each (3), matching fault scope (2), limitation (1). Check: RAID is storage redundancy, not a general processor voter.

Hard practice — question demand

Replicas fail together.

Plan / choice of method

Model the failure or boundary first, then apply these page-specific concepts in order: Fault→error→failure.; spatial/temporal/design redundancy needs independence.; rollback checkpoint/backward vs forward recovery. Finish by checking the final state against the deadline, security property, consistency contract, or performance requirement.

Worked answer

Common code/config/input/region defeats replicas; use diversity/fault domains, test failover and durable recovery—more replicas alone insufficient.

Mark-winning points

Credit requires the complete method sequence, explicit verification of the conclusion, and the limiting assumption/trade-off—not merely the recommended technology.

Common trap

Claiming every Hamming/RAID configuration has the same correction ability.

Topic-specific traps and diagnosis

  • Assuming replicas are independent without discussing common-mode failure.
  • Calling detection alone recovery.
  • Claiming every Hamming/RAID configuration has the same correction ability.

Exam marking checklist

  • Have I stated what fault is tolerated?
  • Did I explain detection, action and limitation?
  • Did I include voter/shared-cause risk?
