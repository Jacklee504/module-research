Real-time Foundations

Use this sheet to distinguish a system that is merely fast from one whose correctness includes timing.

Purpose, scope and examiner demand

Real-time engineering makes a result useful at the required time. The central exam habit is to name the timing requirement, the consequence of missing it, and the metric that exposes the problem.

Exam focus by part

  • Hard miss fails, soft degrades.
  • C,T,D, U=ΣC/T.
  • RM fixed/EDF deadline/CE frames.
  • assumptions determine proof.

Question-demand diagnosis and answer plan

  1. Underline whether the question is about hard, firm, soft, or safety-critical behaviour.
  2. State the deadline and what happens on a miss.
  3. Separate computation time, response time, latency, jitter, and throughput.
  4. Give one relevant design control: reservation, admission control, bounded scheduling, buffering, or redundancy.

Question-type cues

  • Application cue: EDF test (1,4),(1,5),(2,10), D=T.
  • Analysis cue: Networked controller misses deadlines.

Definitions, notation and discriminating comparisons

  • Deadline: latest acceptable completion time. WCET: safe upper bound on execution time.
  • Hard real-time: a deadline miss is unacceptable; firm: late output has no value; soft: quality degrades rather than fails.
  • Latency: end-to-end delay. Jitter: variation in delay. Throughput: completed work per unit time.
  • Response time = release-to-completion delay. A basic feasibility check is response time ≤ deadline.

Step-by-step methods and solution routes

For a camera brake detector, first identify the event: obstacle detected at time 0. Next identify the required action: braking command by 20 ms. If the computation takes 5 ms but queueing and communication add 18 ms, response time is 23 ms. Since 23 > 20, the design fails even though the processor is fast. Reduce blocking/queueing, reserve capacity, or shorten the work; then re-check the whole path.

Worked examples and method extensions

Question

Classify an airbag controller and a video player; explain why average speed alone is insufficient.

Model answer

An airbag controller is hard real-time: an action after its deadline may be dangerous, so a bounded worst-case response is required. A video player is usually soft real-time: a late frame reduces perceived quality, but the system can continue. Average speed hides occasional long delays; a real-time claim needs a worst-case or bounded latency argument, and jitter matters for the video stream.

Mark-winning points

Credit requires the named mechanism, all intermediate values or protocol states, the final conclusion, and these topic checks: Hard miss fails, soft degrades.; C,T,D, U=ΣC/T.; RM fixed/EDF deadline/CE frames.; assumptions determine proof.

Common trap

Graded practice and hard extensions

Prompt 1 - 6 marks

Explain hard, firm, and soft real-time with one example each. Exam bridge: define each (3), state deadline-miss consequence (2), relate one metric (1). Check: do not call every safety-related system hard without explaining its deadline.

Prompt 2 - 8 marks

A service has 8 ms computation, 4 ms queueing, and 6 ms network delay with a 15 ms deadline. Assess it and propose two improvements. Exam bridge: add the path (3), compare to deadline (1), give targeted controls (4). Check: 8+4+6=18 ms, not 15 ms.

Hard practice — question demand

Networked controller misses deadlines.

Plan / choice of method

Model the failure or boundary first, then apply these page-specific concepts in order: Hard miss fails, soft degrades.; C,T,D, U=ΣC/T.; RM fixed/EDF deadline/CE frames. Finish by checking the final state against the deadline, security property, consistency contract, or performance requirement.

Worked answer

Measure release/execution/blocking/end-to-end delay, schedule/admit work, bound locks/shed noncritical load and verify hyperperiod/residual overload.

Mark-winning points

Credit requires the complete method sequence, explicit verification of the conclusion, and the limiting assumption/trade-off—not merely the recommended technology.

Common trap

Forgetting queueing, interrupt, and communication delay.

Topic-specific traps and diagnosis

  • Equating real-time with high throughput or a fast CPU.
  • Using mean delay as evidence for a hard deadline.
  • Forgetting queueing, interrupt, and communication delay.

Exam marking checklist

  • Have I named the deadline and miss consequence?
  • Have I used latency/jitter/throughput accurately?
  • Have I checked the end-to-end worst-case path?
