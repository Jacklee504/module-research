Symmetric Crypto and Perfect Security

Define security precisely, then connect it to ciphers and finite examples.

Purpose

This topic turns definitions into small proof-like answers. Be able to distinguish shared-key operation from public-key operation, explain perfect secrecy, and reason about a cipher's key/message possibilities rather than merely saying it is “strong”.Exam use: Quantifiers, distributions, compatible-key count and every OTP condition are stated before the conclusion.

What the question asks, and plan

  1. State the experiment: plaintext, randomly selected key, ciphertext observed by an adversary.
  2. Give the formal condition or counting/probability argument.
  3. Apply it to the specified scheme, including assumptions on keys.
  4. For LFSR/block/stream parts, define the object and show the requested state/period calculation.
  5. Question interpretation: For define, write the quantified probability equality; for prove, count compatible keys for each message/ciphertext; for critique, test key distribution, length, secrecy and reuse.

Terms and formulas

  • Symmetric cipher: communicating parties share a secret key for encryption/decryption.
  • Perfect secrecy: P(M=m | C=c)=P(M=m) for every possible m,c; seeing ciphertext changes no message probability.
  • One-time pad: c=m⊕k, with uniformly random, secret, message-length key used once.
  • Block/stream cipher: transforms fixed blocks / combines plaintext with a keystream, commonly by XOR.
  • LFSR: a shift register whose feedback is a linear mod-2 combination; a non-zero degree-r state has period at most 2ʳ−1.
  • Rapid recall: Perfect secrecy means P(M=m|C=c)=P(M=m) for every relevant m,c; OTP achieves it only with a uniform secret key at least as long as the message and never reused.

Derivation and method

For the one-time pad and any fixed m,c, exactly one key k=m⊕c produces c. If all keys are equally likely, every message is equally compatible with that ciphertext, so the posterior equals the prior. Reusing a pad breaks this: c₁⊕c₂=m₁⊕m₂, leaking a relationship. For an LFSR, write the state order and feedback taps before shifting; do not infer a maximal period without proof.Exam workflow: Fix arbitrary m and c, solve for the unique key, use uniformity to calculate the conditional probability, and state exactly where the argument fails if a key is reused.

Fully worked simple example

Let messages and keys be two bits, each key uniform. For observed c=10, message m=00 needs k=10; message m=01 needs k=11; similarly each message has exactly one key. Thus each remains probability 1/4 after observing c: this toy one-time pad is perfectly secret. If the same key encrypts m₁=01,m₂=11, then c₁⊕c₂=10=m₁⊕m₂, which is leakage.

Medium/hard paper-style synthesis

Let two two-bit messages use the same OTP key. If c1=01 and c2=10, then c1 xor c2=11=m1 xor m2. If the attacker knows m1=00, they recover k=01 and m2=c2 xor k=11. Thus each ciphertext alone had the OTP counting property, but reuse creates a deterministic relation and destroys perfect secrecy for the joint experiment.

Two graded prompts

1. Foundation — 6 marks

Give the conditions under which a one-time pad has perfect secrecy. Exam bridge: random/uniform key (2), as long as message (1), secret (1), used once (2). Check: computational difficulty is not the reason.

2. Exam bridge — 8 marks

Contrast block and stream ciphers and explain why repeating a stream-cipher keystream is dangerous. Check: describe data unit/keystream and derive the XOR relation between two plaintexts.

Hard paper-style synthesis

Paper-style synthesis: messages {0,1} have priors 3/4 and 1/4 and C=M xor K with uniform K. For c=0, compute the posterior. Check P(C=0)=1/2, P(M=0,C=0)=3/8, so P(M=0|C=0)=3/4, unchanged; the nonuniform message prior does not prevent OTP perfect secrecy.

Common mistakes

  • Calling any large-key cipher perfectly secure.
  • Omitting the distribution and single-use assumptions.
  • Equating an LFSR's possible maximum period with its actual period.
  • Confusing encryption confidentiality with authentication.
  • Recovery rule: Do not replace information-theoretic equality with 'brute force is difficult'; those are different security claims.

Checklist

  • Formal condition or compatibility argument present?
  • Key assumptions explicit?
  • Bit operations and state order shown?
  • Security claim limited to what was proved?
