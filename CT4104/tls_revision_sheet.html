TLS

Explain secure-channel components by the security job each performs.

Rapid exam refresher

  • TLS negotiates, validates peer, derives traffic keys and protects records.
  • certificate checks chain/SAN/validity/status.
  • ephemeral agreement gives forward secrecy.
  • TLS is not authorisation.

Purpose, scope and examiner demand

TLS is explicit CT4104 scope and illustrates analysis of cryptographic network protocols.

Exam focus by part

  • TLS negotiates, validates peer, derives traffic keys and protects records.
  • certificate checks chain/SAN/validity/status.
  • ephemeral agreement gives forward secrecy.
  • TLS is not authorisation.

Question-demand diagnosis and answer plan

State endpoints and threats; explain authentication, key establishment and protected application data; then identify configuration or validation failure.

Question-type cues

  • Application cue: Why reject trusted certificate with wrong SAN?
  • Analysis cue: TLS terminates at load balancer then clear HTTP reaches backends.

Definitions, notation and discriminating comparisons

  • Handshake: negotiate parameters and establish keys.
  • Certificate: server identity-to-public-key evidence.
  • Key exchange: derives shared session secrets.
  • Session keys: symmetric keys protecting data.
  • Authenticated encryption: confidentiality plus tamper detection.

Step-by-step methods and solution routes

  1. Name client, server and active/passive attacker.
  2. Validate the server certificate and intended hostname.
  3. Describe key establishment and derived session keys.
  4. Explain authenticated protection of application data and a failure case.

Reasoning checkpoints

  1. Use and justify: TLS negotiates, validates peer, derives traffic keys and protects records.
  2. Use and justify: certificate checks chain/SAN/validity/status.
  3. Use and justify: ephemeral agreement gives forward secrecy.
  4. Use and justify: TLS is not authorisation.

Worked examples and method extensions

A browser validates shop.example’s certificate, completes a key exchange, then uses fresh symmetric session keys for encrypted, integrity-protected requests. Skipping hostname validation permits a certificate for another site to mislead the client.

Exam-paper-led practice

Practice question 1 [medium/hard]

Scenario and demand: A browser connects to payments.example; the chain is trusted and current, but the leaf SAN is only api.example. Explain the required result and the handshake checks behind it. [8 marks]

Question-demand diagnosis and fastest route: The browser must reject: hostname identity is a separate certificate check. It validates the chain signatures to a trusted anchor, validity/status policy, permitted key usage and SAN match, then negotiates an authenticated TLS connection and derives traffic keys. A trusted CA signature says the issuer signed the certificate, not that it names the requested host. Trap: accepting “any certificate from a trusted CA” enables misbinding.

Practice question 2 [medium/hard]

Scenario and demand: TLS terminates at a load balancer, then clear HTTP crosses a shared backend network. Assess the design and improve it. [9 marks]

Question-demand diagnosis and fastest route: TLS protects only to the termination point. Between load balancer and backend, credentials and requests can be read or changed by a network attacker. Re-encrypt with authenticated TLS/mTLS on the backend hop, restrict network paths, validate forwarded identity headers only from the trusted proxy, and apply application-level authorisation. Forward secrecy protects past traffic if ephemeral session keys are later lost, but does not authorise an admin endpoint. Trap: “TLS is on” is not an end-to-end claim.
