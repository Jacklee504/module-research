CT4104 Topic Guide

Threat analysis

Make security decisions traceable from assets and threats to mitigations and residual risk.

Rapid exam refresher

  • Model assets, actors, flows and trust boundaries.
  • threat/vulnerability/risk differ.
  • STRIDE is a prompt not answer.
  • cue: asset→path→impact→control→residual.

Purpose, scope and examiner demand

Threat analysis supports CT4104’s security-assessment outcome by turning an informal system description into prioritised security reasoning.

Exam focus by part

  • Model assets, actors, flows and trust boundaries.
  • threat/vulnerability/risk differ.
  • STRIDE is a prompt not answer.
  • cue: asset→path→impact→control→residual.

Question-demand diagnosis and answer plan

Describe system and trust boundaries; list assets and attackers; identify threats and vulnerabilities; prioritise impact/likelihood; select mitigations and residual risk.

Question-type cues

  • Application cue: Threat-model browser/API/database/email appointment service.
  • Analysis cue: “HTTPS completes our microservice threat model.” Challenge it.

Definitions, notation and discriminating comparisons

  • Asset: something worth protecting.
  • Attack surface: reachable entry points.
  • Threat / vulnerability: harmful event / exploitable weakness.
  • Mitigation / residual risk: treatment / risk remaining after treatment.
  • STRIDE: spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege.

Step-by-step methods and solution routes

  1. Draw components, data flows and trust boundaries.
  2. List assets and plausible authorised/unauthorised actors.
  3. Use STRIDE or equivalent to find threats per boundary.
  4. Rate consequences, choose proportionate controls, then record residual risk.

Reasoning checkpoints

  1. Use and justify: Model assets, actors, flows and trust boundaries.
  2. Use and justify: threat/vulnerability/risk differ.
  3. Use and justify: STRIDE is a prompt not answer.
  4. Use and justify: cue: asset→path→impact→control→residual.

Worked examples and method extensions

A login service stores password hashes and issues sessions. Spoofing risk: credential theft; mitigation: phishing-resistant MFA and rate limits. Information disclosure risk: verbose login errors; mitigation: generic errors and protected logs. These controls reduce rather than guarantee zero risk.

Worked answer

Common trap

Graded practice and hard extensions

Foundation

Is a missing access check a threat? Check: it is a vulnerability; unauthorised data access is a resulting threat/event.

Exam bridge

Threat-model a student web application. Check: include assets, boundary, at least two threats, impact, controls and residual risk.

Hard practice — question demand

“HTTPS completes our microservice threat model.” Challenge it.

Plan / choice of method

Model the failure or boundary first, then apply these page-specific concepts in order: Model assets, actors, flows and trust boundaries.; threat/vulnerability/risk differ.; STRIDE is a prompt not answer. Finish by checking the final state against the deadline, security property, consistency contract, or performance requirement.

Worked answer

HTTPS is channel protection only; model service/queue/storage/admin boundaries and add mTLS, object auth, validation, secrets rotation and monitoring.

Mark-winning points

Credit requires the complete method sequence, explicit verification of the conclusion, and the limiting assumption/trade-off—not merely the recommended technology.

Common trap

Ignoring abuse by authenticated users.

Topic-specific traps and diagnosis

  • Listing controls without assets or threats.
  • Calling every risk “high” without rationale.
  • Ignoring abuse by authenticated users.

Exam marking checklist
