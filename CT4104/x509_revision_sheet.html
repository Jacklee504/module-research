X.509 certificates

Trust a public key only after validating its identity binding and chain for the intended use.

Rapid exam refresher

  • Certificate binds SAN/subject and key via issuer signature.
  • path/key constraints/validity/status/hostname all matter.
  • CSR is request, not trust.
  • cue: leaf-to-root route.

Purpose, scope and examiner demand

X.509 is explicitly named in CT4104 and supplies the identity-to-public-key binding used by TLS-style systems.

Exam focus by part

  • Certificate binds SAN/subject and key via issuer signature.
  • path/key constraints/validity/status/hostname all matter.
  • CSR is request, not trust.
  • cue: leaf-to-root route.

Question-demand diagnosis and answer plan

Describe the claimed identity and key, then walk through issuer signature, chain, hostname, time and intended-use checks.

Question-type cues

  • Application cue: Validate leaf L via intermediate I to root R for api.example.
  • Analysis cue: Evaluate permanent leaf pinning.

Definitions, notation and discriminating comparisons

  • Certificate: signed identity–public-key binding.
  • CA / trust anchor: issuer / configured trusted root.
  • Chain: leaf through issuers to a trust anchor.
  • SAN: hostname identity field.
  • Revocation: certificate should no longer be accepted.

Step-by-step methods and solution routes

  1. Read the presented name and public key.
  2. Verify signatures to a configured trust anchor.
  3. Check validity time, hostname/SAN and key usage.
  4. Apply revocation policy and reject a failed check.

Reasoning checkpoints

  1. Use and justify: Certificate binds SAN/subject and key via issuer signature.
  2. Use and justify: path/key constraints/validity/status/hostname all matter.
  3. Use and justify: CSR is request, not trust.
  4. Use and justify: cue: leaf-to-root route.

Worked examples and method extensions

For bank.example, a browser verifies a current leaf certificate, its chain and signatures, and that the SAN matches bank.example. A valid certificate for evil.example remains unacceptable.

Exam-paper-led practice

Practice question 1 [medium/hard]

Scenario and demand: Validate a leaf for api.example: leaf L is signed by intermediate I, I by root R; L is valid today and has DNS:api.example. State every path decision before accepting it. [9 marks]

Question-demand diagnosis and fastest route: Build L→I→R to a locally trusted root, verify each signature, check validity intervals, basic/path-length and key-usage constraints, leaf EKU for server authentication, hostname SAN and applicable revocation/status policy. Acceptance follows only if every check succeeds; the public key alone is not identity. Trap: treating a supplied intermediate as trusted without validating its issuer and constraints.

Practice question 2 [medium/hard]

Scenario and demand: A team proposes permanently pinning today’s leaf certificate in its mobile app. Evaluate the proposal. [8 marks]

Question-demand diagnosis and fastest route: Pinning can reduce reliance on a misissued publicly trusted certificate, but a permanent leaf pin makes routine renewal, key rotation and incident recovery an outage unless the app is updated. If pinning is justified, plan backup pins for future keys/intermediates, protected update channels, expiry/rollover tests and emergency revocation. Normal PKI hostname/path validation remains necessary. Trap: pinning an expiring leaf is not the same as managing trust safely.
