OpenSSL

Use a cryptographic library by defining the desired property and evaluating its configuration.

Purpose, scope and examiner demand

Using and evaluating cryptographic libraries such as OpenSSL is an official CT4104 learning outcome.

Exam focus by part

  • Tool commands require safe parameters and secret handling.
  • protect private keys from logs/history/source control.
  • distinguish key/CSR/certificate/chain.
  • inspect SAN/issuer/EKU.

Question-demand diagnosis and answer plan

State the intended property; identify inputs, keys/certificates and trusted configuration; describe a safe verification test; explain why defaults or successful output are insufficient evidence.

Question-type cues

  • Application cue: Obtain and verify TLS certificate safely.
  • Analysis cue: A developer proposes `openssl enc` with a password to protect a database export. Explain the security limitation and give a safe implementable alternative.

Definitions, notation and discriminating comparisons

  • Key pair: public/private asymmetric keys.
  • CSR: certificate signing request.
  • PEM: common textual encoding for keys/certificates.
  • Cipher suite/configuration: selected protocol algorithms and settings.
  • Verification: independently check a signature, chain or connection property.

Step-by-step methods and solution routes

  1. Specify confidentiality, integrity, authentication or certificate task.
  2. Protect private keys and identify trust inputs.
  3. Use standard library/protocol facilities rather than custom cryptography.
  4. Inspect outputs and independently verify intended properties.

Reasoning checkpoints

  1. Use and justify: Tool commands require safe parameters and secret handling.
  2. Use and justify: protect private keys from logs/history/source control.
  3. Use and justify: distinguish key/CSR/certificate/chain.
  4. Use and justify: inspect SAN/issuer/EKU.

Worked examples and method extensions

For a signed release, protect the signing private key, sign the release digest, distribute the public certificate/key through a trusted channel, and verify the signature before deployment. A command returning success does not prove recipients trust the right key.

Exam-paper-led practice

Practice question 1 [medium/hard]

Scenario and demand: Deploy TLS for api.example.edu. The CA receives a CSR whose common name is correct but whose SAN contains only www.example.edu. Describe the safe issue-and-verify workflow. [9 marks]

Question-demand diagnosis and fastest route: Fastest route: generate a protected private key with restrictive permissions, create a CSR requesting DNS:api.example.edu, obtain authorised issuance, then inspect issuer, validity, key usage/EKU and the SAN. A client verifies the signed chain to a trust anchor and matches the hostname to SAN, so it must reject this certificate for api.example.edu. A CSR is only a request, not trust. Trap: CN does not rescue a missing/wrong SAN.

Practice question 2 [medium/hard]

Scenario and demand: A developer proposes password-based openssl enc for nightly database exports. Assess it and give an implementable authenticated design. [8 marks]

Question-demand diagnosis and fastest route: Confidentiality alone is insufficient: modification must be detected and password/nonce/key lifecycle must be defined. Use a reviewed application with OpenSSL’s EVP AEAD API, for example AES-GCM: generate a random data key and unique nonce, encrypt with versioned metadata as associated data, store the authentication tag, and keep the key in protected key management rather than shell history. Decryption verifies the tag before using plaintext. Trap: inventing a CLI GCM workflow is not a safe substitute for an authenticated design.
